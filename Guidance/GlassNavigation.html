Glass navigation

Settings → Appearance → Floating glass navigation (experimental) enables independent glass controls in the main window's left navigation column. The column is invisible: it has no background, edge or continuous shadow. Each control has its own rounded optical surface and bounded shadow; space between objects shows the underlying display. Existing layout, reveal and hit targets remain unchanged. It is off by default. The top toolbar, wider adjacent panels, detached windows, image processing and exported images keep their existing behavior.

The blur pipeline and static dither adapt the MIT-licensed OverShifted/LiquidGlass implementation. It is vendored as selected shader source, not an OverEngine dependency. The blur kernel's separate Jam3 MIT attribution is retained too. See source pins and adaptation details.

One backdrop copy with a bounded 16 logical-pixel sampling neighborhood and two half-resolution seven-tap blur passes serves the entire visible column. Individual objects reuse it, so neither another object's shadow nor its foreground becomes a lens input. Sharp original vector icons use adaptive solid light/dark ink, without an outlined halo. Neutral hover/selection feedback and project-pill markings share that ink. One restrained response layer, capped at 12.5 percent before theme and disabled alpha, avoids stacked washes obscuring the glass; selected controls still gain a distinct hover response. A neutral bottom dash identifies keyboard focus, independently of the persistent left selection marker; glass mode suppresses ImGui's colored navigation outline without disabling navigation. Dirty outlines and automatic-project marks retain their meanings. Press feedback immediately lowers the virtual body toward its backdrop and slightly compresses the glyph inside the unchanged hit target, with interruptible release easing. The body retains its curvature and thickness; one normalized elevation changes the optical gap and the projected shadow together. Pointer drag-out releases visual pressure without changing ImGui activation rules, while keyboard activation does not depend on the pointer position. Hidden or disabled glass rendering does not replay stale press animation when it returns. Existing reduced-motion behavior remains in use.

Reusable motion API

The dependency-free src/Animation subsystem owns presentation motion, not input or project edits. ScalarChannel supplies deterministic tween, exponential and spring transitions from an explicit time step; compose channels for position, size, radius, opacity or optical elevation. ControlMotion combines hover, pressure, selection and focus into one frame snapshot. Its owner is the actual control/view: fixed navigation controls live with the rail, and each workspace owns its pill state. Destruction releases that state without a global identity map. App/ControlMotionAdapter.h reads the existing ImGui item without creating another target. The material consumes the snapshot and current geometry separately.

Call Retarget to interrupt toward a new target, Reverse to return toward the opposite endpoint, Replay to explicitly restart, Cancel to stop in place, or Finish to reach the current target. Repeated same-target requests, including after cancellation, do not restart motion or replace its parameters; a changed live style requires an explicit replay or the next target transition. Repeat counts are additional traversals, capped at 32. Restart jumps to the original start between traversals; ping-pong animates between endpoints. Reverse targets the opposite original endpoint and restarts the configured repeat policy. Spring velocity is retained across spring retargeting; other modes restart from the current value. Springs may overshoot, so adapters must clamp properties with physical bounds, such as opacity or a nonnegative radius. Reduced motion reaches the current target without replaying the repeat sequence. Generic channels cap one time step at .25 seconds; the control adapter deliberately retains its previous .05-second cap and .01 settling tolerance. A missing frame, replaced identity or invisible control resets stale presentation, and repeated reads of one frame return the same control snapshot.

SliderMotion maps the supplied authoritative value onto finite normalized endpoints, including reversed ranges, while sharing the control response. Position stays immediate during dragging and keyboard changes; it never writes the value, delays the native slider return, or commits an edit. A repeated frame may carry a newer authoritative slider value even though its control snapshot is unchanged. Degenerate or nonfinite ranges report validRange=false and position zero. Native activation, release and explicit cancellation remain the widget's responsibility; animation completion is not a successful slider release or an undo/history operation.

Use an owner-local AnimationController only when lifecycle observation is needed. It issues typed owner/track identities and queues Started, ReachedStart, ReachedEnd, Repeated, Completed and Cancelled records with a run generation. These describe presentation transitions, not application actions. Configure small finite capacities for the owning view. Accepted transitions reserve their complete event budget, so a delayed drain cannot stall an accepted animation or silently lose its lifecycle. A new request that exceeds capacity returns EventCapacityExceeded without changing the track; handle that result. Remove an owner/track when its view goes away. Removal invalidates identities and discards their pending events silently rather than firing teardown callbacks. Controller-scope identities also prevent drained events or handles from being adopted by another or replacement controller.

using namespace Stack::Animation;
// Retain these with the view, not in a drawing function's static storage.
AnimationController motion({1, 4, 64});
const auto owner = motion.CreateOwner();
const auto height = motion.CreateTrack(owner, 1.f);
// Native input remains authoritative. These are presentation requests only.
// On native activation: motion.Snap(owner, height, .2f);
// On native release: motion.Retarget(owner, height, 1.f, MotionSpec::Spring());
// On explicit cancellation: motion.Cancel(owner, height); then choose a reset.
motion.Advance(deltaSeconds, reducedMotion);
const auto visual = motion.Read(owner, height); // use visual->value if present
// After drawing, drain a fixed batch BEFORE dispatching any reactions.
AnimationEvent batch[64];
const auto count = motion.DrainEvents(batch, 64);
for (std::size_t i=0; i<count; ++i) {
    const auto& event = batch[i];
    if (event.kind == EventKind::Completed && motion.IsCurrent(event)) {
        // Optional visual-state reaction only. New events await the next drain.
    }
}
// On view teardown: motion.RemoveOwner(owner);

The example separates input lifecycle from visual lifecycle and does not wire completion to project actions. Dispatching a drained copy avoids callbacks inside channel advancement or rendering; check owner/generation again before acting on delayed results. The subsystem and its consumers are UI-thread presentation state, not a thread-safe job scheduler. Existing GPU material failures remain explicit; scalar UI timing is not a CPU image-processing fallback.

Focused tests are registered as StackAnimation.Core and StackAnimation.Controls when BUILD_TESTING is enabled. They require no GPU or user images. From a C++17 compiler environment they can also be built directly with the corresponding tools/tests/animation_*_tests.cpp and src/Animation/*.cpp. Headless checks remain active in release builds; the optional component probe explicitly keeps its assertions enabled. The optional Linux EGL component probe exercises production ImGui/GlassChrome behavior separately; it is not a shipping dependency or a Windows application test.

Motion design evidence and limits

Apple’s Motion guidance distinguishes stronger direct-touch feedback from quieter trackpad behavior. The following principles guide Stack; they are not copied Apple timings or an exhaustive account of every platform state.

  • Idle, hover and press: keep frequent desktop interactions restrained, acknowledge contact immediately, and allow drag-out cancellation/re-entry. See Designing Fluid Interfaces. Persistent selection and keyboard focus remain separate from pressure.
  • Drag and release: direct manipulation follows the authoritative input. A spring can receive signed incoming velocity without dividing by distance, including when starting at its target. SpringTo(target, velocity, spec) is an explicit new handoff generation; velocity uses the animated value’s units per second. Invalid velocity/target or a non-spring specification leaves the track unchanged. Supplied velocity applies to the first traversal; repeats restart at rest. See Animate with springs.
  • Slider endpoints: Apple’s UIKit slider demonstration shows transient lens stretch and momentum, not proof of an out-of-range numerical value. Keep value limits/ticks with the native control and bound decorative width, elevation and overscroll separately.
  • Interruption, entry and exit: preserve current presentation and stable identity when intent changes. Spring retargeting retains velocity; a fresh tween does not promise velocity continuity. Grouped surface morphs need coordinated geometry/identity above scalar channels; this framework does not automatically fuse nearby controls. See UI animations and transitions.
  • Completion and accessibility: the engine’s Completed is numerical settlement, not perceptual or business completion. Never delay input/actions for the spring tail. Reduced motion finishes decorative motion promptly; it is not a slower bounce. Reduced transparency and contrast are separate material preferences, not synonymous animation flags.

Independent analyses by Rauno Freiberg and Emil Kowalski reinforce interruption, continuity and purposeful feedback. NN/g’s critique warns that repeated wiggles and moving targets can consume attention. These are design observations, not measurements of Apple’s equations or proof of Stack’s latency. Existing desktop button timings remain Stack defaults. The optional slider demonstration uses explicitly illustrative settings; it does not change shipping slider behavior.

Optical model and upstream adaptations

Stack retains the attributed upstream blur kernel and static dither. The optical body is original Stack code: a shallow closed convex volume formed by sweeping an ellipsoid over a planar rectangle. Circular icon buttons are the zero-core ellipsoid case; project pills are capsules. One orthographic view ray enters the front surface, refracts into glass, intersects the actual exit patch and refracts back into air. The outgoing ray intersects a virtual backdrop plane. Front and exit normals come from the same volume, so thickness changes both magnification and shoulder curvature rather than applying an unrelated UV displacement.

A bounded analytic intersection examines the side/corner quadrics and flat caps, with no unbounded ray marching, scene geometry, acceleration structure or temporal accumulation. The material uses an index of refraction of 1.45 and a half-depth of 32 percent of the smaller object dimension. Reflected rays intersect a finite virtual overhead rectangular emitter. A distant panoramic studio window adds a restrained broad lower-shoulder reflection: its angular support stays above the backdrop plane and away from the clear center. A broad, low-energy front/upper environment lobe makes the face visible even when transmission is black. It follows the same reflected direction and Fresnel response, with smooth support only above the backdrop plane; it is not a gray opacity fill. These are art-directed studio lights, not Apple-calibrated emitters, a painted stripe or uniform outline. Navigation buttons, project pills and the activity control explicitly use a quieter NavigationControl material role: its panoramic-window radiance is 65 percent of the default Lens role. This is a semantic choice, not a pixel-size threshold, so UI/font scaling and framebuffer DPI do not silently change the treatment. The default Lens retains the accepted stronger showcase reflection. Shape, magnification, overhead strip, shadow and interaction behavior are identical between roles. The environment lights add fixed arithmetic without another ray, texture sample or render pass. Fresnel blends reflected and transmitted energy in linear light. The local neutral ambient remains backdrop-derived; the directional lights do not impose a constant bias on the reflection-dominated rim. Black transmission alone cannot reveal glass, and absorption or a shadow cannot brighten black; the added face visibility comes from reflected illumination. The single-ray budget explicitly approximates untraced internal reflection with the front reflected environment; total internal reflection never becomes a zero-direction texture lookup. Reflected backdrop detail and dispersion are not enabled. Missing capture coverage smoothly returns to the modeled environment rather than sampling uninitialized capacity.

The soft underside shadow is a bounded occlusion approximation from a broad near-overhead studio fill, separate from the grazing strip used for reflection. Its offset, projected scale and penumbra follow the virtual object height and fill geometry. A signed-distance CDF approximation feathers both sides of the projected boundary instead of adding a constant dark perimeter. It is captured neither into the glass nor into image processing. The virtual environment and shadow are not a complete physical simulation, and this is not Apple's private renderer. Original image data and exports are untouched.

Boundaries and cost

The renderer owns one reusable set of three RGBA8 textures and framebuffer objects on the main UI context. Capacity is reserved for the column plus its bounded sampling neighborhood and retained through reveal/hide animation. Valid-region clamping excludes unused capacity from both sharp and blurred sampling. The rail is capped at four million source pixels, or 24 MiB including its two half-resolution targets. Ordinary narrow-rail allocations use much less. The material uses one soft texture sample and at most one sharp transmitted sample per covered pixel; exterior shadow pixels need no texture samples. Each object has a narrow output apron derived from the same projected shadow layout used by the shader, clipped to its approved backdrop column and caller clip. There is one material draw per visible object, but capture and blur are shared. Foreground contrast adds one bounded compute dispatch using the existing blurred capture, plus two small buffers totaling 6 KiB for up to 128 items. Nine samples per item are averaged in linear light, and separate 0.16/0.22 switch thresholds keep slight backdrop changes from rapidly flipping the ink. Persistent identity-based slots retain history while controls reorder or projects scroll; recycled slots reset through identity guards. Fully clipped controls consume no slot. There is no image readback, CPU effect implementation, extra backdrop copy or processing-texture mutation.

The framebuffer copy contains display-encoded UI pixels. The shared blur remains in that display domain. Optical radiance composition converts sampled colors to linear light and converts the result back to display encoding; it does not access scene-linear HDR image buffers. sRGB conversion is disabled only during this material pass and restored afterward. RGB and alpha use separate source-over blend factors so antialiased glass and shadow edges preserve an opaque destination. A narrow, clipped shadow apron surrounds each object as part of the optional UI overlay. It does not change image data, export pixels or hit/layout bounds, and stays in the approved left column, including its shared top toggle when the left panel owns that control. Disabling glass removes the entire treatment. This is a UI material, not a color-grading operation.

Failure and compatibility

GPU initialization or allocation failure latches a diagnostic shown by Stack's notifications. Small opaque cores underneath the individual objects keep controls readable if the material fails, without restoring a continuous sidebar or emulating glass on the CPU. The error remains visible; switching the option off selects normal navigation. Turn the option off and on to retry. Disabling the option or shutting down releases its GPU resources on the owning context. Foreground callbacks require a successful current-frame capture; clipped or off-capture controls retain ordinary palette rendering rather than reading stale pixels.

This version intentionally covers only controls in the main-window left navigation column. It does not change detached viewport rendering or promise Apple Liquid Glass visual equivalence. Normal appearance remains available by switching the option off, including when reduced transparency is preferred.

Current quality tradeoffs

Keep the single-ray material until a replacement improves native-size appearance and motion, not just enlarged still images. Focused cloud experiments did not justify shoulder supersampling, dispersion or an additional internal reflection: five-tap shoulder sampling gave marginal visible improvement with about 27 percent higher warm software-render time in its matched component fixture; separate color-channel rays introduced moving colored speckles; a later shared-ray, bilinear-filtered RGB-offset approximation avoided obvious static speckles but showed no convincing native-size benefit in matched 1x/2x comparisons, so its two extra texture reads were rejected before motion or timing expansion; grazing reflected-backdrop sampling, including a filtered variant, retained undersampling artifacts; one consistently weighted internal bounce added a localized glint rather than the reference's broad lower shoulder and sparkled under fractional motion. In the inspected glint pixels, second intersections remained valid, but the secondary energy weight varied steeply between samples, so softening only the emitter is not an established fix. A separate 20-percent blend toward the existing blurred capture at the refracted coordinate produced little native-size benefit on patterned content and did not justify its extra texture sample; it was also rejected. A NavigationControl-only central-face blend toward the blurred refracted sample was also rejected: rich media/editor-like stress scenes showed only slight native-size softening while competing text remained. Its clear shoulder and default Lens were preserved, but the result did not justify production adoption. None of these experiments is enabled. These findings are specific to the tested geometry and fixtures, not universal limits on those techniques.

Design references

Context matters when comparing materials. Fresh WWDC design-system examples soften document/photo content outside the controls as well as inside them; this is not evidence that the glass shader alone produces their legibility. Stack keeps independent objects and untouched gaps rather than importing a continuous scroll-edge strip. Apple’s shared sampling-region guidance supports capturing nearby content before any glass, ink or shadow is drawn. A focused production-renderer probe verifies pixel-identical neighboring objects when their order reverses, influence from a feature inside the capture apron, and no influence after that feature moves outside the crop. Rich procedural/editor-like fixtures expose possible glyph/background competition, but are stress scenes: the current AppShell layout normally reserves the rail width rather than placing image content behind it.

Apple's Meet Liquid Glass and New look of app icons informed visual assessment: emphasize lensing, preserve transmitted color and give each floating control a curved optical surface without a second continuous glass layer behind it. Actual examples from Apple’s Materials guidance, the WWDC session and dated release imagery are compared at approximately matched optical-body sizes, with source crops and synthetic Stack backdrops distinguished. Small controls often use quieter, uneven reflections than enlarged conceptual slider beads; media controls and Regular/Clear materials also differ, so there is no single reference treatment to copy. Even the Clear example visibly softens backdrop detail. These comparisons guide restrained per-role illumination rather than removing the approved raised volume or treating every icon as a large showcase lens. Independent explanations by Kube and Victor Baro informed the bevel/lighting approach; they are approximations, not documentation of Apple's private implementation. NN/g's usability critique reinforces keeping foreground controls sharp and readable. No Apple reference image or code is included. The OverShifted and Jam3 source adaptations are separately attributed as described above.
