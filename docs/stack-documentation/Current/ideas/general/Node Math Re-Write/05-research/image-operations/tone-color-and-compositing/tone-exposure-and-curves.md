## Purpose

Tone operations change how numerical intensity is distributed. Many are pointwise, but the same formula can look radically different in scene-linear light, encoded sRGB, a camera log encoding, or a perceptual lightness space. Therefore **Brightness**, **Gamma**, **Contrast**, and **Filmic** are UI names—not complete mathematical specifications.

A production Stack node should state at least: input/output state, intensity basis (per-channel RGB, luminance, luma, or perceptual lightness), exact formula/order, pivot/reference values, treatment of negative and HDR values, clipping policy, and alpha behavior. The current graph cannot carry this state on an `Image` wire, so the statuses below describe implementation, not correctness for every input.

Recommended architecture: keep exposure, affine math, power/log, interpolation, and curve lookup as primitives; build Levels, lift/gamma/gain, shadows/mids/highlights, filmic/view transforms, and automatic tone tools as convenience compounds.

## Primary tone controls

| Stable ID | Operation | Canonical formula / algorithm | Scope | Required domain / state | What it does / common uses | Composition cautions | Current Stack status based on audit |
|---|---|---|---|---|---|---|---|
| `TONE.EXPOSURE` | Exposure | `rgb_out = rgb_in · 2^EV` | Pointwise RGB; alpha unchanged | Scene-linear light in known RGB primaries; signed/HDR policy | Photographic stop-based scaling; one EV doubles light | On encoded RGB it is merely nonlinear code-value gain; clipping should be a later explicit stage | **Implemented RAW-specifically** after WB/camera transform; no general Exposure node |
| `TONE.GAIN` | Multiplicative gain | `y = g·x` | Pointwise scalar or RGB | Numeric state explicitly named | Scale intensity, signal calibration, simple white gain | Mathematically identical to multiply; only call it exposure in linear light with `g=2^EV` | **Implemented** through DataMath Multiply; no dedicated image-gain contract |
| `TONE.OFFSET` | Offset | `y = x + o` | Pointwise scalar or RGB | Numeric; encoding and units named | Move black and white levels together; pedestal | Changes zero; can create negative or >1 values; invisible clipping changes the operation | **Implemented** through DataMath Add; Brightness is an RGB offset followed by clamp |
| `TONE.LIFT` | Lift | No universal formula; define a selected shadow-weighted offset or named grading model | Pointwise/tonally weighted | Chosen grading model, pivot and encoding | Raise/lower darker tones preferentially | Do not document “lift” as a formula-free primitive; different grading systems produce different results | **Absent** as a standalone control; shadow logic exists inside compounds |
| `TONE.GAMMA_GRADE` | Gamma grading | Common normalized convention: `y=max(x,0)^(1/γ)`; signed extension optional | Pointwise | Usually normalized nonnegative values; exponent convention | Midtone shaping while retaining 0/1 endpoints | Not the sRGB transfer function; some tools use exponent `γ` instead of `1/γ`; negative policy is essential | **Node-specific**: LUT has Gamma 2.2 modes; other shaders use `pow`; no generic adjustable node |
| `TONE.LGG` | Lift / gamma / gain | A named ordered composition, e.g. `gain · pow(max(x+lift,0),1/γ)`; exact model must be selected | Pointwise compound | Explicit grading model/encoding/order | Familiar three-control primary grade | Order, pivots, negative handling, channel coupling, and clipping vary; do not confuse with ASC CDL | **Absent** as a general node |
| `TONE.PRINTER_LIGHTS` | Printer lights | Per-channel additive exposure/density increments in a specified log/printing-light model | Pointwise RGB compound | Named log/density encoding and printer-light step size | Film-style coarse RGB exposure/color timing | Not simply RGB addition in arbitrary data; units and neutral-step convention are implementation-specific | **Absent** |
| `TONE.BRIGHTNESS` | Brightness | **Ambiguous by name**; choose offset, gain, luma shift, or perceptual-lightness method | Pointwise or luma-derived | Method and state must be visible | Familiar general lightness control | A stable UI name may wrap several explicit methods; never infer the formula from “brightness” alone | **Implemented as one specific method**: `rgb'=clamp(rgb+amount,0,1)`; Stable lifecycle |
| `TONE.CONTRAST` | Linear contrast | `y = p + c(x-p)` | Pointwise | Chosen pivot `p`, encoding/intensity basis, clip policy | Expand/compress distances around a pivot | Encoded-space contrast is a look operation; linear-light contrast changes radiometric ratios; RGB-independent use can shift hue | **Implemented** as `(rgb-.5)·(1+amount)+.5`, then clamp; Stable |
| `TONE.CONTRAST_PIVOT` | Contrast pivot | Parameter `p` in `p+c(x-p)` | Pointwise parameter | Same state as Contrast | Choose the tone held fixed during contrast change | A pivot is not a separate pixel transform without contrast; expose as a parameter/value input | **Absent as an exposed control**; current Contrast hard-codes `0.5` |

## Levels and tonal zones

| Stable ID | Operation | Canonical formula / algorithm | Scope | Required domain / state | What it does / common uses | Composition cautions | Current Stack status based on audit |
|---|---|---|---|---|---|---|---|
| `TONE.LEVELS` | Levels | `u=(x-black)/(white-black)`; optional clamp; midpoint via a declared power/curve; output remap optional | Pointwise compound | `white≠black`; normalized or declared code range | Set black/white points and reshape midtones | UI gamma convention/order varies; clipping and output levels must be independent options | **Composable partially** with DataMath/Mask Remap; no general image Levels node |
| `TONE.BLACK_POINT` | Black point | Usually lower-end remap `u=(x-b)/(w-b)` and/or explicit clip below `b` | Pointwise parameterized | Declared paired white/output range | Choose which input maps to output black | “Move” and “clip” are different methods; avoid destroying below-black data unintentionally | **No dedicated image node**; embedded in Tone/View logic |
| `TONE.WHITE_POINT` | White point | Usually upper-end remap paired with black point | Pointwise parameterized | Declared paired black/output range | Choose which input maps to output white | A display white point in colorimetry is not this scalar white-level control | **No dedicated image node**; embedded in Tone/View logic |
| `TONE.SHADOWS` | Shadows adjustment | `out = combine(in, adjust(in), w_shadow(L))` | Pointwise with tone-derived weight | Named tone metric `L`, weight curve and adjustment method | Target dark regions | Weighting may be based on encoded luma, linear luminance, or EV; color and halo behavior differ | **Compound support only**: 3-Way Grade, hidden Tone Equalizer, RAW develop; no generic standalone node |
| `TONE.MIDTONES` | Midtones adjustment | Blend through a bell/band weight `w_mid(L)` | Pointwise with tone-derived weight | Named `L`, center, width and falloff | Target middle tones | “Midtone” location changes with transfer and scene exposure; overlapping zone normalization matters | **Compound support only** in 3-Way Grade/Tone tools |
| `TONE.HIGHLIGHTS` | Highlights adjustment | Blend through a high-tone weight `w_high(L)` | Pointwise with tone-derived weight | Named `L`, transition and adjustment method | Target bright tones | Highlight compression is not highlight reconstruction; RGB-channel clipping complicates weights | **Compound support only**; compiled Shadows/Highlights path is not browser-registered |
| `TONE.TONE_EQUALIZER` | Multi-band tone equalizer | `out` from overlapping EV/luma-band weights and per-band gains, normalized across bands | Pointwise after tone classification; sometimes local | Named metric/bands/falloff; optional spatial smoothing | Fine control over several tonal zones | Band weights and exposure state must be explicit; local smoothing changes it into a neighborhood operation | **Implemented but hidden**: Rec.709-luma Gaussian EV-band gains |

## Curves and roll-off

| Stable ID | Operation | Canonical formula / algorithm | Scope | Required domain / state | What it does / common uses | Composition cautions | Current Stack status based on audit |
|---|---|---|---|---|---|---|---|
| `TONE.CURVE` | Tone curve | `y=f(x)` from a monotonic/nonmonotonic spline or sampled 1D LUT | Pointwise lookup | Declared domain/range, interpolation, extrapolation, channel basis | Arbitrary tone mapping | Curve resolution, interpolation, endpoint behavior, monotonicity, HDR extrapolation, and pre/post state are part of the operation | **Implemented as Tone Curve, NeedsFix**; CPU builds a 256-sample RGBA16F LUT that clamps values to `[0,1]`; curve is not wireable |
| `TONE.RGB_CURVE` | Shared RGB curve | `out=(f(R),f(G),f(B))` using the same `f` | Pointwise RGB lookup | Named RGB encoding/primaries | Neutral-preserving per-channel tone shaping | Neutral RGB stays neutral, but a nonlinear shared curve can still change RGB ratios, hue, and saturation | **Available only through the compound Tone Curve behavior; no reusable shared-curve primitive/value** |
| `TONE.CHANNEL_CURVES` | Per-channel curves | `out=(f_R(R),f_G(G),f_B(B))` | Pointwise RGB lookup | Named encoding; three curve definitions | Tone and color shaping simultaneously | Strong hue shifts and noninvertibility are expected; curve endpoints and channel clipping matter | **RAW has optional per-channel curve work; no general discoverable per-channel-curves node confirmed** |
| `TONE.S_CURVE` | S-curve | A monotonic curve with slope >1 through mids and compressed toe/shoulder | Pointwise curve preset | Declared pivot/domain and spline/function | Conventional contrast look | “S-curve” is a shape family, not one formula; preserve it as a preset over a visible curve | **Composable** in Tone Curve; no separate preset contract |
| `TONE.FILMIC` | Filmic tone curve | A named toe/mid/shoulder function or spline; no universal canonical formula | Pointwise compound | Scene/display state, exposure reference, target peak/black, chosen model | Compress wide scene range into display range with smooth roll-off | “Filmic” is not a standard. Hable, ACES, sigmoid, and camera curves differ materially | **Implemented only as part of View Transform/Tone systems**, not a generic named filmic operator |
| `TONE.TOE` | Toe | Lower-end segment `f_toe(x)` joined continuously to the midsection | Pointwise curve component | Join point, slope/continuity, black target | Smooth shadow compression/roll-off | A toe may raise, compress, or crush shadows; “avoids clipping” is not guaranteed | **Embedded** in View Transform; no standalone primitive |
| `TONE.SHOULDER` | Shoulder | Upper-end segment `f_shoulder(x)` joined continuously to mids | Pointwise curve component | Join point, slope/continuity, peak target | Smooth highlight compression/roll-off | A shoulder maps high values but cannot reconstruct clipped capture data | **Embedded** in View Transform; no standalone primitive |
| `TONE.SIGMOID` | Sigmoid contrast | Example logistic normalized to chosen endpoints, or named rational sigmoid | Pointwise | Defined function, midpoint, slope, domain and normalization | Smooth S-shaped contrast with bounded response | “Sigmoid” is also a family; raw logistic does not hit exact 0/1 on finite input without normalization | **Absent** generically |
| `TONE.VIEW_TRANSFORM` | Scene-to-display tone/view transform | Ordered compound: exposure/reference mapping → tone scale → gamut handling → display encoding | Pointwise/may include global metadata | Named scene space, display gamut, peak/black, viewing state, output transfer | Make scene-referred values display-ready | Tone mapping, gamut mapping, and OETF are separate stages even if one node presents them together | **Implemented as View Transform, Stable**, with tone/gamut compression and final clamp **but no output OETF**; output is display-mapped linear RGB |

## Key ambiguity notes

- **Exposure versus brightness:** exposure is a linear-light multiplication by `2^EV`; Stack’s current Brightness is an offset followed by clipping.
- **Gamma versus transfer function:** a grading power is not sRGB, Rec.709, PQ, HLG, or a camera log curve. Use exact named encode/decode transforms.
- **RGB curve versus luminance curve:** applying `f` independently to RGB preserves neutral inputs but can change colored hue/saturation. A luminance-preserving tone operation needs a chosen luminance model and a ratio/chroma strategy.
- **Tone mapping versus highlight recovery:** tone mapping compresses available high values; recovery estimates data lost during capture.
- **Filmic:** use the word only as a category/preset label unless the actual function and target display contract are shown.

## Recommended Stack treatment

- Add explicit general Exposure, Levels, named Transfer Encode/Decode, Curve, and ASC CDL nodes.
- Store curves as reusable graph values with domain, interpolation, extrapolation, and monotonicity metadata.
- Keep View Transform compound, but split its declared contract into scene tone scale, gamut mapping, and output encoding; fix the missing OETF.
- Let familiar nodes expose a compact method selector rather than silently changing semantics: Brightness `{offset, gain, perceptual}`, Contrast `{encoded, linear, perceptual}`, Curve `{RGB, luminance, per-channel}`.
- Preserve negative and >1 scene values until a deliberate output stage. Make every clamp visible in the node contract.
