STACK COLOR-GRADING / IMAGE-MATH CONVERSATION HANDOFF
====================================================

PURPOSE OF THIS FILE

This is a handoff summary for continuing the conversation in a new ChatGPT thread. It captures the subject, the tone, the design philosophy being explored, the conclusions reached so far, and the unresolved questions. It intentionally does not reproduce the very large tables of image operations from the previous conversation. Instead, it explains what those tables contained and why they were created.

PROJECT CONTEXT

The user is building an image-editing program called Stack. Stack uses a visual node graph, broadly inspired by systems such as Unreal Engine’s material or shader graphs. Images enter the graph, pass through connected processing nodes, and eventually reach an output or viewport.

Stack is intended to be flexible, technical, and transparent. The user does not want it to behave only like a conventional photo editor where controls such as “brightness,” “contrast,” or “saturation” conceal all of the underlying math. The larger goal is to let users construct real image-processing pipelines from understandable building blocks while still allowing friendlier, higher-level tools to exist.

The current implementation includes at least one basic color-grading node with shadows, midtones, and highlights controls. Each tonal region has a Dear ImGui-style color picker that can tint that portion of the image. This led into a broader discussion about how professional editors organize grading controls, what the controls actually do mathematically, and how Stack should represent color spaces and image data inside the graph.

TONE AND CONVERSATIONAL STYLE

The conversation has been exploratory, informal, and deliberately “nerdy.” The user has mostly been thinking aloud, correcting or refining ideas mid-sentence, and trying to build a mental model before writing implementation prompts for Codex.

The preferred response style is patient, beginner-friendly, and technically honest. The user wants correct terminology, but not terminology used as a substitute for explanation. The discussion should frequently translate familiar editing names into the lower-level operations they may represent.

The useful pattern has been:

6. Identify where the user’s intuition is correct and where hidden complications exist.
7. Turn the conclusions into questions that can later be asked of an implementation AI in Codex.

The user is not asking for an implementation pass yet. The immediate goal is understanding, architecture planning, and producing strong diagnostic questions for Codex.

MAIN TOPIC: COLOR GRADING AS EXPLICIT IMAGE MATH

The central idea is that most image-editing controls are mathematical functions applied to image data. Names such as brightness, contrast, saturation, shadows, highlights, temperature, or vibrance are useful interface abstractions, but those names do not uniquely specify the underlying operation.

For example, a control called “brightness” could mean:

- adding a constant to RGB values,
- multiplying RGB values,
- applying a power or gamma curve,
- moving perceptual lightness,
- altering only a luminance component,
- or applying a specially shaped tone curve.

Those methods can produce very different results. Therefore, Stack should ideally avoid treating a friendly name as though it were a complete mathematical definition.

The user’s preferred direction is to allow most nodes to behave like visual-programming or shader-graph nodes: a node receives numerical image data, performs a defined function, and outputs numerical image data. The graph should not necessarily attempt to infer the user’s artistic intent or secretly repair every questionable connection.

At the same time, higher-level convenience nodes can still exist. A “Contrast” or “Three-Way Color” node might internally use several lower-level operations. Ideally, the user could inspect, understand, or eventually expand those higher-level nodes into their component math.

COLOR SPACE, ENCODING, AND LINEAR LIGHT

A major source of confusion was the distinction between sRGB and linear light.

The important clarification is that “linear sRGB” and ordinary encoded sRGB can use the same RGB primaries and white point. The difference is the transfer encoding applied to the numbers.

In linear-light data:

- a value of 0.5 represents half as much light as 1.0,
- doubling a value corresponds to doubling represented light,
- light addition, exposure scaling, and many compositing operations behave physically and mathematically as expected.

In ordinary sRGB-encoded data:

- the stored values are transformed by a nonlinear transfer curve,
- the code values devote more precision to darker visible differences,
- the numeric midpoint is not half the physical light output.

A concrete example discussed was an 8-bit gray value of 128. If the stored sRGB code value is simply multiplied by two, it reaches approximately 255 and clips to white. If 128 is first decoded to linear light, doubled there, and then encoded back to sRGB, the result is only around 175–176. That example was used to show that the same apparent “multiply by two” operation can mean radically different things depending on the encoding of the input values.

The phrase “linear-light encoding” should be explained as: the pixel numbers are proportional to represented light. It does not mean the image must look correct if those raw linear numbers are sent directly to an ordinary display. A view or output transform is still needed to encode them appropriately for the display.

EXPLICIT COLOR-CONVERSION NODES

The user proposed adding an explicit converter or transform node to Stack. A possible chain would be:

Input image in sRGB encoding
→ decode or convert to linear
→ perform image math or grading
→ convert back to sRGB encoding
→ output or display

This design was considered valid and aligned with the user’s philosophy.

The exact naming is still unresolved. Possibilities include:

- Color Space Transform
- Color Transform
- Encoding Transform
- Transfer Function
- Decode / Encode
- Convert Color Space

A useful distinction will eventually be needed between:

1. Transfer-function changes, such as sRGB encoded to linear sRGB.
2. RGB color-space changes, such as sRGB primaries to Display P3 or Rec. 2020.
3. White-point or chromatic-adaptation transforms.
4. Scene-to-display or view transforms.
5. LUT-based look transforms.

One “converter” node could expose several of these modes, but it may become clearer to separate them or clearly label exactly which part of color representation is changing.

DUMB NODES VERSUS COLOR-AWARE NODES

The user does not want every node to be overly smart. The preferred analogy is Unreal Engine: nodes are visual building blocks, and connecting them is a form of programming.

In that model, a multiply node should simply multiply. It should not secretly decide that the input must be converted to linear first. A saturation node should have an explicitly defined algorithm rather than silently adapting itself to whatever it receives.

The main risk is silent semantic mismatch. A graph may be numerically valid while being conceptually wrong. For example:

- exposure-like multiplication may be applied to sRGB-encoded values,
- a LUT may receive a color space it was not designed for,
- a blend mode may be evaluated in linear light even though the expected appearance assumes encoded RGB,
- a hue operation may receive ordinary RGB values even though it expects a hue-based representation,
- premultiplied alpha may be treated as straight alpha.

The recommended compromise is:

- keep operations explicit and mostly non-magical,
- carry descriptive metadata with image connections,
- display warnings rather than automatically changing the data,
- allow advanced users to make unusual or intentionally “wrong” pipelines,
- make it easy to see what kind of buffer is traveling through a wire.

WIRE LABELS AND VIEWPORT LABELS

The user suggested placing small centered text labels on node connection lines. These could identify things such as:

- RGB image
- red, green, or blue channel
- mask
- alpha
- sRGB
- linear
- another color space or encoding

This was considered a strong idea, although the labels should be designed carefully so the graph does not become visually noisy.

A more complete wire label may eventually need to distinguish:

- channel layout: RGB, RGBA, scalar, mask, depth, vector, etc.
- RGB primaries or working color space: sRGB, Display P3, Rec. 2020, ACEScg, etc.
- transfer encoding: linear, sRGB, gamma, log, PQ, HLG, etc.
- alpha state: straight or premultiplied
- data range: normalized, HDR, signed, unrestricted float, and so on

The viewport could show compact status text such as:

Buffer: Linear sRGB
View: sRGB Display Transform

This is more precise than merely saying “linear,” because a buffer and the way it is currently being viewed are separate concepts.

PROFESSIONAL EDITOR ORGANIZATION

The conversation briefly considered Photoshop, Lightroom, and other professional tools. The broad observation was that professional applications organize tools around user-facing mental models rather than exposing every internal formula.

Common groupings include:

- global or primary correction,
- tone shaping,
- color balance,
- curves,
- selective color relationships,
- local masks and regions,
- input and output color management,
- look creation,
- finishing and output.

Curves are especially important because they visualize a mapping from input values to output values. Different curves can represent:

- overall RGB tone,
- separate red, green, and blue mappings,
- hue versus hue,
- hue versus saturation,
- hue versus luminance,
- luminance versus saturation,
- saturation versus saturation,
- mask or opacity remapping.

Some professional tools also allow the user to click directly on the image and drag. Under the hood, the software samples the selected pixel or region, determines where it lies on the relevant curve or color axis, and moves the corresponding control point. The direct manipulation is therefore another interface for editing a mathematical mapping.

This remains an area for later, deeper research. The current conversation established the conceptual direction but did not finish a detailed comparison of Photoshop, Lightroom, Camera Raw, DaVinci Resolve, and other grading systems.

PER-PIXEL OPERATIONS AND THE LIMITS OF “JUST THIS PIXEL”

The conversation then zoomed out from color grading to image operations in general.

The key distinction is not really “math versus non-math.” Every digital image operation is implemented mathematically. The more useful distinction is what information the operation needs.

A processing operation may depend on:

- only the current pixel,
- multiple channels of the current pixel,
- nearby pixels,
- a large neighborhood,
- statistics from the whole image,
- another image or mask,
- multiple frames,
- metadata or calibration information,
- camera or lens profiles,
- user intent,
- a trained model.

Examples of pure pointwise operations include addition, multiplication, power functions, clamping, channel mixing, matrices, curves, thresholds, and many blend operations.

Examples that need neighboring pixels include blur, sharpening, edge detection, convolution, morphology, demosaicing, local contrast, and many denoisers.

Examples that require whole-image analysis include automatic exposure, automatic levels, histogram equalization, normalization, palette extraction, and global noise estimation.

Examples that require external information include accurate camera color correction, RAW interpretation, lens correction, dark-frame subtraction, display proofing, and color-chart calibration.

Examples that use trained or semantic models include neural denoising, object removal, subject detection, depth estimation, generative fill, and learned automatic grading.

This framing supports the user’s core idea. Most current Stack nodes can be explicit math nodes. More complex nodes can be added later with additional data requirements, multi-pass processing, specialized visual design, metadata inputs, or model attachments.

The tables covered these broad categories:

The reason for creating the catalog was not to demand that Stack immediately implement every operation. LOW-LEVEL PRIMITIVES AND HIGH-LEVEL CONVENIENCE NODES

The strongest architecture idea reached so far is a two-layer system.

Low-level primitives could include things such as:

- scalar add, subtract, multiply, divide, and power,
- clamp, remap, threshold, and interpolation,
- vector and RGB math,
- split, merge, and swizzle channels,
- matrices and channel mixers,
- curves and lookup tables,
- explicit transfer-function and color-space conversions,
- coordinate transforms and sampling,
- convolution and neighborhood operators,
- histogram or reduction operations,
- masks, blending, and compositing.

Higher-level nodes could include:

- Exposure
- Brightness
- Contrast
- Levels
- Lift / Gamma / Gain
- Three-Way Color
- Split Toning
- Temperature and Tint
- Vibrance
- Clarity
- Hue-versus-Saturation
- LUT
- Filmic Tone Mapping

A higher-level node could either be implemented directly for speed or internally represented as a reusable node group. The important design goal is that its behavior should be documented and, ideally, inspectable.

For example, a conceptually transparent Exposure node could be described as:

Decode to linear if needed
→ multiply RGB by 2 raised to the EV value
→ preserve unrestricted float values unless clipping is explicitly requested
→ later encode or transform for display

A conceptual three-way color node could be described as:

derive a tonal measure
→ generate overlapping shadow, midtone, and highlight weighting functions
→ apply three color adjustments
→ combine the weighted results

A hue-versus-saturation tool could be described as:

convert into a representation with hue and chroma or saturation
→ use hue as the input to a one-dimensional control curve
→ use the curve result to scale chroma or saturation
→ convert back to the desired RGB space

These examples show how a familiar editing control can be treated as an understandable graph of lower-level operations.

IMPORTANT TERMINOLOGY TO KEEP CLEAR

Several terms should not be casually collapsed into one another:

Color space:
Usually includes primaries, white point, and often an associated transfer function, though software sometimes uses the term loosely.

Primaries:
The chromaticities that define what the RGB axes mean.

Transfer function or encoding:
The mapping between stored numerical values and linear-light values. sRGB’s nonlinear encoding is one example.

Linear light:
Values proportional to represented light.

Gamma:
Often used loosely. It may mean a simple power-law encoding, a display response, or a midtone control. The exact meaning should be stated.

Luma:
A weighted signal computed from encoded RGB in a specified video system.

Luminance:
A physical or colorimetric measure related to light.

Lightness:
A perceptual dimension used in color-appearance spaces.

Saturation:
An overloaded term. Different RGB, HSL, HSV, Lab, LCh, OKLab, and grading algorithms define it differently.

Chroma:
Distance from a neutral axis in certain color spaces; related to but not identical to saturation.

Brightness:
A user-facing term that does not define a unique formula.

Exposure:
Most cleanly represented as multiplicative scaling in scene-linear light, commonly using 2^EV.

View transform:
The mapping used to make the current working or scene-referred buffer appear correctly on a display.

Look transform:
A creative or stylistic transform, distinct from the purely technical display mapping.

OPEN QUESTIONS FOR THE NEXT CONVERSATION

The next discussion should probably continue by turning these ideas into a structured set of questions for Codex to inspect Stack’s current implementation.

Important questions include:

1. What numerical image format travels between current Stack nodes?
   Examples: 8-bit integer, 16-bit integer, half float, 32-bit float.

2. Are imported PNG and JPEG images decoded from sRGB into linear values, or are their encoded channel values uploaded and processed directly?

3. Does Stack currently store any color-space or transfer-function metadata with an image buffer?

4. Does the OpenGL texture format preserve values outside 0–1, or are values clamped during intermediate processing?

5. Does the viewport apply an sRGB transfer function, use an sRGB framebuffer, or simply display shader output directly?

6. Which existing nodes assume encoded RGB, and which assume linear-light data?

7. What exactly does the current shadows/midtones/highlights color node do mathematically?

8. How are the shadow, midtone, and highlight weighting regions calculated?
   Are they hard ranges, smooth masks, luminance curves, or something else?

9. What definition of luminance or luma is currently used?

10. Are alpha values straight or premultiplied?

11. Can connection wires carry metadata without forcing automatic conversions?

12. Can the graph display small data-type and color-state labels on connections?

13. Should mismatched connections cause an error, a warning, or no intervention?

14. Can higher-level nodes be represented internally as reusable subgraphs or node groups?

15. Can curves be stored as reusable data and evaluated efficiently on the GPU?

16. Can the viewport distinguish the working buffer from the current display/view transform?

17. What minimum set of primitive math nodes would reproduce a useful portion of the current editor?

18. Which operations require a second GPU pass, reductions, histograms, pyramids, or neighborhood sampling?

19. How should LUT nodes declare their expected input and output color spaces?

20. Should one general Color Transform node handle transfer functions, RGB matrices, white-point adaptation, and gamut conversion, or should those remain separate nodes?

21. How can Stack remain permissive like a shader graph while still making technically suspicious pipelines visible to the user?

CURRENT OVERALL CONCLUSION

The user’s intuition is substantially correct.

Stack can be designed so that most nodes are explicit functions over image data rather than opaque editing commands. The system does not need every node to be “smart” or to silently understand artistic intent. However, image numbers do not carry enough meaning on their own. Their interpretation depends on information such as transfer encoding, color primaries, alpha state, range, and sometimes scene or display context.

The best compromise reached so far is:

- explicit conversion nodes,
- transparent mathematical operations,
- descriptive metadata on wires,
- compact buffer and view information in the viewport,
- warnings instead of forced corrections,
- primitive nodes for technical users,
- higher-level convenience nodes for normal grading work,
- and inspectable definitions for familiar controls.

The spirit of the project is not to imitate Photoshop or Lightroom exactly. It is to borrow their useful visual interactions and grading concepts while making the underlying image pipeline much more visible, modular, and programmable.
