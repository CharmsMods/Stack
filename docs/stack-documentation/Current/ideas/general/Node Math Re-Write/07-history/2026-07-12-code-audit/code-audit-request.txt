======================================================================
1. WHY THIS AUDIT EXISTS
======================================================================

Stack is intended to become a flexible, technical, and transparent image editor built around a visual node graph. Images enter the graph, pass through connected processing nodes, and eventually reach a viewport or output/export stage.

The long-term design direction being explored is a hybrid, two-layer node system:

1. Low-level operations that expose explicit image math and data transformations.
2. Higher-level convenience operations that provide familiar editing controls while being internally documented, inspectable, and—where practical—constructed from or expandable into lower-level operations.

The central analogy is “math Legos.” A large portion of conventional image editing can be described as smaller mathematical operations combined in a deliberate order. For example, familiar names such as Brightness, Contrast, Saturation, Vibrance, Three-Way Color, Levels, Clarity, Dehaze, or Tone Mapping often hide several lower-level steps. However, this analogy must not be oversimplified. Some operations work independently on each pixel, while others require neighboring pixels, whole-image statistics, additional images, multiple passes, metadata, calibration information, coordinate resampling, or specialized algorithms.

The later research phase will create detailed operation-reference documents and propose an architecture for composing reliable higher-level edits from lower-level primitives. Before that research can be trusted, it needs accurate ground truth about what Stack already does. Your report will supply that ground truth.

Do not assume the desired architecture already exists. Do not assume that current behavior is correct simply because it is implemented. Do not redesign or implement the future system during this audit. Establish what exists, what it actually does, what is only planned, what is unclear, and what capabilities or constraints the current architecture presents.

2. PRODUCT PHILOSOPHY YOU MUST KEEP IN MIND
======================================================================

The future direction is not to force users to build every normal edit manually from dozens of tiny math nodes. Backend composability, technical transparency, and user-facing node granularity are separate design decisions.

The desired balance is:

- Explicit, factual, shader-graph-like primitives for technical users.
- Friendly higher-level nodes for ordinary editing work.
- Clear definitions of what each operation actually does.
- Inspectable or expandable compound operations where practical.
- A manageable node library and category system rather than hundreds of poorly organized entries.
- A permissive graph that does not secretly “fix” every unusual connection.
- Descriptive data/color metadata and warnings for technically suspicious connections instead of forced automatic conversions wherever possible.
- A visually polished UI without hiding all underlying behavior.
- Conventional, deterministic image processing as the main focus of this work—not neural networks, generative AI, semantic models, or AI workflow design.

Friendly editing names are not mathematical specifications. For example, “brightness” could mean adding a constant, multiplying encoded values, scaling scene-linear light, changing perceptual lightness, modifying a luma component, applying a gamma/power curve, or applying a custom tone curve. Your audit must determine the current formula or algorithm rather than inferring it from the displayed name.

The numerical/color context is also part of an operation’s meaning. Important distinctions include:

- Ordinary nonlinear sRGB-encoded RGB versus linear-light RGB using sRGB primaries.
- Primaries/white point versus transfer function/encoding.
- Scene-referred data versus display-referred data.
- Working-buffer transform versus view/display transform versus creative look transform.
- Luma versus luminance versus perceptual lightness.
- Chroma versus the many incompatible definitions of saturation.
- Straight alpha versus premultiplied alpha.
- Normalized 0–1 data versus unrestricted floating-point data that may contain negatives or values above 1.

Exposure is most cleanly defined as scaling scene-linear RGB by 2^EV. That does not mean Stack currently works this way; determine what the code actually does.

A desirable future pipeline might explicitly decode an input transfer function, perform appropriate math in a declared working representation, and apply a view/output transform later. Again, do not assume Stack currently does this.

4. EVIDENCE STANDARD
======================================================================

Every important claim about Stack must be tagged as one of these:

- VERIFIED: Directly supported by active code, a runtime trace, a test, or a build configuration that selects the code.
- INFERRED: Strongly suggested by the code, but not completely provable without runtime behavior, missing assets, external dependencies, or additional context.
- DOCUMENTED ONLY: Stated in documentation/comments/plans but not confirmed by the active implementation.
- UNKNOWN: Not determinable from the repository as it currently exists.
- CONTRADICTED: Documentation, naming, comments, UI labels, or separate code paths disagree.

For verified and inferred claims, cite:

- Exact repository-relative file path.
- Relevant class, struct, function, method, shader, registry entry, enum, field, or configuration target.

When a displayed node name and implementation semantics differ, report both. When comments disagree with code, treat active code as stronger evidence and record the contradiction. D. Inspect formulas and algorithms

E. Inspect architectural facilities needed for future composition

Investigate the graph’s type system, compound/group/subgraph support, serialization, UI parameter system, shader/pipeline abstraction, multi-pass support, caching, warnings, validation, testing, and numerical safety.

F. Cross-check

- Compare code with documentation and previous plans found in the repository.
- Check for duplicate or legacy rendering paths.
- Check whether viewport and export traverse the same processing path.
- Check whether CPU and GPU implementations of the same operation agree.
- Check whether preview resolution, proxy textures, or cached outputs change behavior.
- Check whether debug/release settings change formats, shaders, precision, or color behavior.

- Many filters can share convolution or neighborhood infrastructure, even when specialized user-facing nodes remain valuable for performance and controls.
- A color wheel is usually a convenience structure involving a tonal mask/weight, a defined color adjustment, and blending—not one universal primitive formula.
- Global operations commonly require reduction passes such as histogram, min/max, sum, mean, variance, or percentile.
- A geometric transform is not only matrix math; sampling method, border behavior, coordinate convention, and output extent are part of its definition.
- Traditional blend modes may be expected in nonlinear encoded RGB and can look materially different in linear light.
- RAW processing may require CFA pattern, black/saturation levels, camera matrices/profiles, white-balance metadata, highlight handling, and other information not recoverable from ordinary RGB pixels alone.

7. QUALITY BAR
======================================================================

The report must be thorough enough that another AI can reason about Stack without guessing how the current code works. Prefer completeness and evidence over brevity, but do not pad the document with generic image-processing explanations that are unrelated to the repository.

Be especially careful about these common mistakes:

- Calling all RGB data “sRGB” without separating primaries from transfer encoding.
- Assuming a value named “gamma” is an encoding function rather than a grading control.
- Assuming 32-bit float automatically means scene-linear or color-managed.
- Assuming an RGBA texture documents straight versus premultiplied alpha.
- Assuming a displayed node name defines its formula.
- Assuming a node file is active without verifying registration and runtime use.
- Assuming OpenGL performs an sRGB conversion without confirming texture formats, framebuffer formats, state, and shader behavior.
- Assuming a color picker’s RGB value is in the same representation as the processed image.
- Ignoring values below 0 or above 1.
- Ignoring implicit clamping from normalized formats, render targets, image encoders, or shader functions.
- Treating a blur as merely per-pixel math without accounting for sampling, border behavior, and passes.
- Treating geometry as merely coordinate matrix math without accounting for reconstruction filters and output extent.
- Treating a UI group/frame as an executable compound node.
- Treating all masks as equivalent to alpha.
- Treating documentation plans as implemented behavior.

When exact math cannot be expressed as one compact equation, provide pseudocode or a staged algorithm and identify every intermediate. When formulas use constants, coefficients, thresholds, pivots, matrices, curves, or kernels, record their exact values and source locations.
