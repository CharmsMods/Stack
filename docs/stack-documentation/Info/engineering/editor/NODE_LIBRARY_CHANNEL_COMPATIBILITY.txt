NODE LIBRARY CHANNEL COMPATIBILITY REPORT
Generated from the current graph/channel renderer behavior.

Purpose
This report explains how the node library behaves now that the graph supports both
full-image streams and channel-derived streams. It classifies nodes by channel-mode
safety so the next source pass can add warnings, metadata, or fixes instead of
guessing case by case.

Current channel model
A socket can behave as a full-image stream or as a channel-derived stream.
Channel identity is metadata inferred from graph lineage, not a separate visible
socket type for every normal node.

Current implementation status
LayerDescriptor now includes channel policy metadata, lifecycle status, browser
visibility, notes, and tags. Layer nodes can display channel lineage and policy notes
near their controls when a channel-derived stream reaches them. The advanced sidebar
also shows the same metadata for selected rich-surface layer nodes.

The intended pattern is:
Image -> Channel Split -> optional normal one-input/one-output effects -> Output
or:
Image -> Channel Split -> optional normal effects -> Channel Combine -> Output

Normal layer nodes do not gain four channel inputs. They keep one image input and
one image output. If a Brightness node receives the R channel from Channel Split,
the Brightness output is still considered an R channel stream.

The approved recombine points are:
Output in channel mode.
Channel Combine.

Channel-mode Output and Channel Combine share the same missing-channel defaults:
Missing R = 0.0.
Missing G = 0.0.
Missing B = 0.0.
Missing A = 1.0.

Reference canvas behavior
For multi-source channel mixing, the output canvas is selected from connected channel
sources in R, G, B, A order.
If R comes from Image A and B comes from Image B, Image A is the reference canvas.
Non-reference channels are sampled over normalized UVs, so they stretch to the
reference canvas. No fit, fill, crop, or preserve-aspect behavior should be attached
to Channel Combine or Output; that belongs in future Reformat/Transform nodes.

Channel compatibility labels
Safe - The node's core behavior is meaningful on full images and single-channel
streams.
Mostly Safe - The node probably works on channel streams, but needs test coverage or
minor UI clarification.
Ambiguous - The node has full-color semantics that may not make sense on a single
channel without explicit behavior.
Unsafe / Rework - The node depends on full-image color, source alpha, or canvas
behavior that conflicts with current channel pipelines.

Safe or mostly safe channel nodes
Brightness - Safe.
Reason: Adds/subtracts scalar intensity. Works naturally on a channel stream.

Contrast - Safe.
Reason: Scalar remap around midpoint. Works naturally on a channel stream.

Box Blur - Safe.
Reason: Neighbor blur is meaningful on scalar channels and masks.

Gaussian Blur - Safe.
Reason: Same as Box Blur, with smoother weighting.

Median Denoise - Safe.
Reason: Median filtering is useful for masks and channel cleanup.

Mean Denoise - Safe.
Reason: Mean filtering is useful for masks and channel cleanup.

Pixelation - Safe.
Reason: Spatial block sampling is meaningful on full images and scalar channels.

Flip - Safe.
Reason: Coordinate remap is meaningful for all raster streams.

Invert Mask, Levels Mask, Threshold Mask - Safe.
Reason: These are scalar operations by design.

Solid Mask, Linear Gradient Mask, Radial Gradient Mask, Noise Mask - Safe.
Reason: Scalar procedural sources.

Channel Split - Safe.
Reason: Source of channel streams.

Channel Combine - Safe.
Reason: Intended recombine point with defined missing-channel defaults.

Output - Safe.
Reason: Intended terminal recombine point with defined full-image/channel modes.

Mostly safe channel nodes
Sharpen - Mostly Safe.
Reason: Uses neighbor sampling and edge contrast. It can sharpen scalar channels,
but may amplify channel noise or create ringing.
Recommended action: Add channel tests and possibly expose "safe for channels" in
metadata.

Non-Local Means Denoise - Mostly Safe.
Reason: Denoising a scalar channel is valid, but algorithm quality should be checked.

Bilateral Filter - Mostly Safe.
Reason: Edge-preserving smoothing can be useful for alpha and masks, but full-color
edge weighting may not match single-channel expectations.

Ordered Dither 8x8, Ordered Dither 4x4, Ordered Dither 2x2 - Mostly Safe.
Reason: Dithering scalar channels is useful, but UI should make it clear that a
single channel will output a single-channel pattern.

White Noise Dither - Mostly Safe.
Reason: Same as ordered dithers.

Interleaved Gradient Dither - Mostly Safe.
Reason: Same as ordered dithers.

Error Diffusion Dither - Mostly Safe.
Reason: Scalar error diffusion is valid, but should be tested for stability.

Halftone - Mostly Safe.
Reason: Tone-to-dot conversion can be useful on single-channel streams, but users
should understand it is operating on the channel as luminance.

Crop - Mostly Safe.
Reason: Crop-in-place is meaningful for channels, but does not resize the canvas.

Rotate - Mostly Safe.
Reason: Coordinate transform is meaningful for channels, but does not resize the
canvas to fit rotated content.

Lens Distortion - Mostly Safe.
Reason: Spatial warp is valid for channels, but edge fill/sampling should be tested.

Heatwave Distortion - Mostly Safe.
Reason: Spatial warp is valid for channels, but channel-only use can create strong
registration changes when recombined.

Ripple Distortion - Mostly Safe.
Reason: Same as Heatwave Distortion.

Jpeg Blocks - Mostly Safe.
Reason: Block artifacts can be applied to channels, but color-compression semantics
should be checked.

DCT Compression - Mostly Safe.
Reason: Block frequency artifacts can be scalar, but implementation may assume color.

Wavelet Compression - Mostly Safe.
Reason: Scalar compression artifacts can be valid, but test coverage is needed.

Edge Overlay - Mostly Safe.
Reason: Edge detection on scalar channels can be useful, but this may be better as
a mask generator or image-to-mask variant later.

Vignette - Mostly Safe.
Reason: On channels this behaves like a spatial channel multiplier/mask. Useful but
should be documented.

Ambiguous channel nodes
Saturation - Ambiguous.
Reason: Saturation is a relationship between color channels. On a single-channel
stream, saturation is likely a no-op or misleading.
Recommendation: Keep for full images. Add channel-policy metadata or warning.

Warmth - Ambiguous.
Reason: Warmth shifts red/blue color balance. On a single channel, the meaning is
unclear unless it is defined as scalar bias.

3-Way Color Grade - Ambiguous.
Reason: Uses luma ranges and RGB color wheels. On a channel stream, tonal range may
still exist but color-wheel behavior is not intuitive.
Recommendation: Full-image-first. If allowed on channels, UI should clearly state
that it treats the channel as grayscale input.

HDR Compressor - Ambiguous.
Reason: Highlight recovery/bloom behavior is color/luma-oriented. Single-channel
use may be valid but should be explicitly tested.

Cell Shading - Ambiguous.
Reason: Posterizes lighting/color bands. Channel use may be useful, but semantics
need documentation.

Palette Rebuild - Ambiguous.
Reason: Palette reconstruction is inherently full-color. Single-channel use needs a
separate scalar palette/mapping story.

Chroma Subsample Compression - Ambiguous.
Reason: Chroma is color information. On a single-channel stream, the node name and
behavior are misleading.

Color Bleed - Ambiguous.
Reason: This is a color-channel smear effect. On a channel stream it might become
a scalar smear, but the current name implies RGB interaction.

Chromatic Aberration - Ambiguous.
Reason: The effect offsets color channels against each other. On a single-channel
stream there are no separate color channels to separate.

Airy Bloom, Glare Rays - Ambiguous.
Reason: Highlight/glare effects are full-image-first. They may be useful on channels
but should be treated as advanced/experimental until tested.

Analog Video (VHS/CRT) - Ambiguous.
Reason: Full-image analog artifact stack. Some sub-effects are scalar, others are
color/luma/noise interactions.

Block Shift - Ambiguous.
Reason: Spatial slices are valid on channels, but after recombination this can cause
intentional or accidental per-channel misregistration. It should be presented as a
creative effect when used on channels.

Noise - Ambiguous / Mostly Safe.
Reason: Noise can be useful on scalar channels, but some modes are color noise and
some are grayscale. Channel policy should expose which mode is being used.

Text Overlay - Ambiguous / Needs Fix.
Reason: Text overlay is registered but text texture generation is currently a C++
placeholder. Channel compatibility should wait until the node works.
Current metadata: Hidden from the add-node browser and marked FullImageOnly until a
real text overlay implementation exists.

Unsafe or rework-needed channel nodes
Alpha Protect - Unsafe / Rework.
Reason: Depends on ExecuteWithSource and original source alpha. In a channel pipeline,
the "original source alpha" may not be the same conceptual alpha the user is editing.
Recommendation: Rework into explicit alpha-channel operations, such as Clamp Alpha,
Preserve Existing Alpha, Replace Alpha, or Alpha From Mask, or hide/remove after
compatibility review.
Current metadata: Deprecated, ReworkBeforeExpose, and hidden from the add-node
browser while keeping the descriptor available for project loading.

Expand Canvas - Rework.
Reason: It pretends to expand canvas inside a fixed render target. This conflicts
with the new reference-canvas model because it does not actually change the output
canvas.
Recommendation: Replace with future Reformat/Canvas Resize nodes that can explicitly
own reference canvas dimensions.
Current metadata: Experimental and ReworkBeforeExpose. It remains visible for review,
but the browser label and node notes mark it as not stable canvas-resize behavior.

Background Remover - Needs Fix.
Reason: It operates on full RGB target-color selection and writes alpha. It can be
valuable in a professional workflow, but it is not a generic channel operator.
Recommendation: Full-image-first. Later it could output a mask/alpha channel instead
of directly patching alpha.

General channel policy recommendation
The first channel policy field now exists in layer metadata. Keep using these values
as source-of-truth labels while tests and warnings get deeper:
ChannelSafe - Scalar or spatial operation with clear channel behavior.
ChannelUsefulWithWarning - Works but may create strong per-channel effects.
FullImagePreferred - Meaningful mostly for full-color images.
FullImageOnly - Should not accept channel-derived streams unless explicitly forced.
ReworkBeforeExpose - Current implementation conflicts with channel model.

UI recommendations for channel mode
Continue showing small channel lineage labels on selected nodes, such as
"Channel stream: R".
When adding a color-only node onto a channel stream, show a warning or badge rather
than blocking immediately.
Keep normal effect nodes one-input/one-output; do not add four-pin variants unless a
future node is explicitly designed for multi-channel processing.
Add tests for Image -> Split channel -> effect -> Output for every registered effect.
Add tests for Image A R plus Image B B into Channel Combine with mismatched sizes.
