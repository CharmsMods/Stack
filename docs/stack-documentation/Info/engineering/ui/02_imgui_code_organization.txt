STACK APPLICATION — IMGUI CODE ORGANIZATION QUALITY ASSESSMENT
===============================================================
Researched from src/ source tree, May 2026

--------------------------------------------------------------------------------
OVERALL ARCHITECTURE: HOW IMGUI CALLS ARE STRUCTURED
--------------------------------------------------------------------------------

ImGui calls are distributed as follows. This is not uniform across modules —
some are well-separated, some are monolithic.

  AppShell.cpp        — Top-level tab bar, modal prompts, splash screen.
                        ImGui calls are self-contained and focused. The only
                        ImGui in this file is the tab bar, two modals, and the
                        splash ProgressBar+Text. Clean.

  EditorModule.cpp    — Owns and orchestrates the Editor DockSpace. Calls
                        m_Sidebar.Render(), m_Viewport.Render(), m_Scopes.Render().
                        Also calls ImGuiExtras::RenderBusyOverlay() when async
                        tasks are running. No other ImGui widgets in this file.
                        Clean separation: EditorModule is a coordinator, not a
                        renderer.

  EditorSidebar.cpp   — ImGui::Begin("Inspector Panel Sidebar") + a tab bar
                        with 4 tabs that delegate immediately to sub-objects.
                        Only 67 lines total. Functions as a thin routing layer.
                        Clean.

  EditorViewport.cpp  — ImGui::Begin("Canvas Viewport") + all interaction
                        logic (zoom, pan, color picking, comparison fade).
                        226 lines. All in one Render() function with no helpers.
                        The color picking magnifier code (lines 143-190) is
                        embedded inline. This is the densest ImGui code in
                        the Editor and could be broken out.

  EditorScopes.cpp    — ImGui::Begin("Scopes Panel") with three scope modes in
                        a tab bar. DrawHistogram(), DrawVectorscope(), and
                        DrawRGBParade() are properly separated into private
                        methods. 191 lines. Reasonably organized.

  LayersTab.cpp       — 69 lines. A list of buttons calling editor->AddLayer().
                        Organized by category using color-coded TextColored
                        headers. Contains no logic besides button dispatch.

  PipelineTab.cpp     — 67 lines. Renders the active layer stack as a list of
                        Selectable items with drag-and-drop reordering and a
                        delete button. Self-contained and simple.

  SelectedTab.cpp     — 26 lines. Delegates immediately to the selected layer's
                        virtual RenderUI(). No logic. Pure dispatch.

  CanvasTab.cpp       — 74 lines. Two buttons (Load Image / Export) and a
                        checkbox for the render-up-to-active flag. Clean.

  BundlerModule.cpp   — RenderUI() delegates to three named private methods:
                        RenderSettingsPanel(), RenderFileTreePanel(),
                        RenderDiagnosticsPanel(). 517 lines total, distributed
                        cleanly. Settings panel is ~180 lines, file tree ~100,
                        diagnostics ~30. Each section has a banner comment.

  LibraryModule.cpp   — 1,822 lines. The single largest UI file. The RenderUI()
                        function is 205 lines (lines 292-497). RenderProjectCard()
                        and RenderAssetCard() are ~130 lines each. The preview
                        popup (RenderPreviewPopup) is very long — not measured
                        completely here but it spans hundreds of lines including
                        the compare viewer, metadata inspector, and all action
                        buttons. All popup rendering methods are private helpers.
                        The decomposition is correct in principle but individual
                        methods are too long to be easily browsed.

  RenderTab.cpp       — 4,046 lines. The largest file in the codebase. Organized
                        via RenderUI() -> RenderToolbar() + RenderBody().
                        RenderBody() calls RenderInspectorPanel(), RenderViewportPanel(),
                        RenderScenePanel(). Modal windows are RenderCameraWindow(),
                        RenderFinalRenderSettingsWindow(), RenderFinalRenderWindow(),
                        RenderTestScenesWindow(). The anonymous namespace at the
                        top (~800 lines) contains purely computational helpers
                        (label functions, projection math, color conversion) that
                        produce no ImGui output themselves. These are well separated
                        from the UI calls. Within RenderInspectorPanel and
                        RenderScenePanel, the code is dense but sectioned with
                        comment banners.

  CompositeModule.cpp — 202,938 bytes. Comparable in scale to RenderTab.
                        Decomposed into RenderToolbar(), RenderLayerPane(),
                        RenderSelectedInspector(), RenderViewInspector(),
                        RenderExportInspector(), RenderStage(),
                        RenderLayerContextMenu(), RenderCanvasContextMenu(),
                        RenderLibraryPicker(), RenderSavePopup(), RenderRenamePopup().
                        The breakdown is granular and named consistently.

--------------------------------------------------------------------------------
SEPARATION OF UI FROM LOGIC: MODULE-BY-MODULE VERDICT
--------------------------------------------------------------------------------

AppShell:
  UI is cleanly separated. m_ShowEditorSavePrompt and m_ShowEditorNamePrompt act
  as frame-deferred boolean flags. The tab switch logic in OnTabChanged() is pure
  data logic and contains no ImGui calls.
  VERDICT: GOOD.

EditorModule:
  No ImGui in the coordinator layer. The Execute()/RenderUI() split is clear.
  Async task logic (RequestLoadSourceImage, RequestExportImage) is entirely
  separate from rendering.
  VERDICT: GOOD.

Layer implementations (AdjustmentsLayer, etc.):
  Each layer has RenderUI() containing only the SliderFloat/Checkbox/etc. calls
  for its own parameters. No layout management. No window management. They operate
  entirely within whatever context the caller has set up.
  VERDICT: GOOD.

LibraryManager.cpp:
  LibraryManager is a backend data/async class that does not contain any ImGui
  calls. It exposes state-query methods (GetImportStatusText(), GetSaveTaskState(),
  etc.) which LibraryModule reads and displays.
  VERDICT: GOOD.

RenderTab.cpp:
  The 800-line anonymous namespace of pure C++ helpers is a strong positive.
  RenderInspectorPanel and RenderScenePanel are long, but because they deal with
  many distinct scene object types (primitives, lights, materials, environment,
  camera, postprocessing), some length is inherent. The helpers EditVec3Field,
  EditColor3Field, DrawReadOnlyColorSwatch, EditStringField wrap ImGui calls into
  reusable functions — this is the best ImGui abstraction pattern in the codebase.
  VERDICT: GOOD with room for further extract.

CompositeModule.cpp:
  The stage rendering and GPU pipeline code (RenderStagePreviewTexture, OpenGL
  calls) is mixed in with the ImGui methods, all in the same file. The GPU
  texture management (SyncLayerTextures, EnsureStagePreviewTargets) lives in the
  same compilation unit as the UI panels. This is the most mixed coupling in the
  application.
  VERDICT: MODERATE. Backend and UI concerns are in the same .cpp. Headers are
  at least cleanly declared.

IMGUI STYLE / THEMING: WHAT EXISTS, WHAT DOESN'T
--------------------------------------------------------------------------------

The application applies ImGui::StyleColorsDark() at initialization (AppShell.cpp
line 99). There is NO custom theme applied after that in the main context. The
dark theme is the entire visual identity.

Overrides done per-widget (not global style):
  - ImGui::PushStyleVar(ImGuiStyleVar_WindowRounding, 0.0f) in AppShell.
  - ImGui::PushStyleVar(ImGuiStyleVar_WindowBorderSize, 0.0f) in AppShell.
  - ImGui::PushStyleVar(ImGuiStyleVar_WindowPadding, ...) in AppShell and
    EditorModule for the workspace child.
  - ImGui::PushStyleColor(ImGuiCol_ChildBg, ...) used in Library project card
    info blocks.
  - ImGui::PushStyleColor(ImGuiCol_WindowBg, ...) used in Library preview modal.
  - ImGui::PushStyleColor(ImGuiCol_Text, ...) used throughout for status text,
    layer category headers, Bundler file-type coloring.
  - ImGui::PushStyleColor(ImGuiCol_PlotLines, ...) used in the Scopes histogram.
  - ImGui::PushStyleColor(ImGuiCol_FrameBg, ...) used in the splash progress bar.
  - ImGui::PushStyleColor(ImGuiCol_PlotHistogram, ...) in splash context.

There is no centralized color token system. Colors are defined as raw ImVec4
literals at point of use. For example:
  - Library category header: ImVec4(0.6f, 0.6f, 0.6f, 1.0f)
  - Bundler HTML color: ImVec4(0.9f, 0.5f, 0.2f, 1.0f)
  - Bundler CSS color: ImVec4(0.3f, 0.7f, 1.0f, 1.0f)
  - Bundler JS color: ImVec4(1.0f, 0.85f, 0.3f, 1.0f)
  - Layer category BASE: ImVec4(0.7f, 0.7f, 1.0f, 1.0f)
  - Layer category COLOR: ImVec4(0.7f, 1.0f, 0.7f, 1.0f)
  - Selection highlight: IM_COL32(80, 160, 255, 255)
  - Locked viewport text: ImVec4(1, 0.5f, 0, 1)

No font loading is done in the main app context. The default ImGui font
(ProggyClean baked in) is used everywhere. CompositeModule loads a separate font
for text layer rendering only (stored in m_DefaultTextFontBytes) but this is not
for the UI itself. The Composite module does embed a large font header
(EmbeddedCompositeFont.h at 1.05 MB).

--------------------------------------------------------------------------------
FRAMEWORK PORTABILITY ASSESSMENT
--------------------------------------------------------------------------------

The ImGui backend is GLFW + OpenGL3. All initialization is in AppShell::Initialize().
The backend is accessed through:
  ImGui_ImplGlfw_InitForOpenGL()
  ImGui_ImplOpenGL3_Init()
  ImGui_ImplOpenGL3_NewFrame()
  ImGui_ImplGlfw_NewFrame()
  ImGui_ImplOpenGL3_RenderDrawData()
  ImGui_ImplOpenGL3_Shutdown()
  ImGui_ImplGlfw_Shutdown()

All of these live exclusively in AppShell.cpp. No module reaches into the ImGui
backend directly except AppShell. The modules only use the platform-agnostic
ImGui:: API. This means swapping the backend (e.g., from GLFW+OpenGL3 to
SDL2+Vulkan, or Dear ImGui to another IMGUI) would only require changes to
AppShell and potentially GLLoader/GLHelpers.

The one notable exception: EditorViewport.cpp calls glDeleteTextures() for
m_CheckerTex in its destructor, and calls glBindTexture/glTexParameteri in
Initialize(). This is non-IMGUI GPU code inside a UI class, which creates a
direct dependency on OpenGL in the viewport class. The texture could be
abstracted behind a handle.

Similarly, CompositeModule.h declares unsigned int texture handles (m_StagePreviewTex,
m_StagePreviewFbo, m_StagePreviewProgram, etc.) directly in the class. These are
OpenGL object IDs, coupling the UI class to OpenGL. Moving to a different GPU
API would require changes to CompositeModule itself, not just AppShell.

RenderTab itself is deeply coupled to the renderer internals via
RenderFoundation::State, but this is inherent to its purpose (configuring and
driving a path tracer).

ASYNC TASK PATTERN: HOW BUSY STATE IS COMMUNICATED TO UI
--------------------------------------------------------------------------------

The Async::TaskSystem provides a background thread pool. Tasks post results back
to the main thread via PostToMain(). State is communicated to the UI via:

  Async::TaskState enum: Idle, Queued, Running, Applying, Failed.
  Async::IsBusy(state) returns true for Queued, Running, Applying.

Each long operation has a corresponding state variable and status text string:
  m_SourceLoadTaskState / m_SourceLoadStatusText (EditorModule)
  m_ExportTaskState / m_ExportStatusText (EditorModule)
  LibraryManager internal save/import/export/load task states.

The UI layer queries IsBusy() and status text each frame. When busy:
  - Buttons are wrapped in ImGui::BeginDisabled()/EndDisabled() to prevent
    interaction.
  - ImGuiExtras::RenderBusyOverlay() draws a dark semi-transparent overlay with
    an animated spinner centered in the current window.

The spinner is a DrawList arc animation in ImGuiExtras::DrawSpinner() using
ImGui::GetTime() to drive the arc phase. This is the only custom animation widget
in the codebase.

--------------------------------------------------------------------------------
IMGUI EXTRA UTILITIES: WHAT EXISTS IN ImGuiExtras
--------------------------------------------------------------------------------

ImGuiExtras (src/Utils/ImGuiExtras.h, ImGuiExtras.cpp) contains exactly two
functions:

  DrawSpinner(label, radius, thickness, color)
    — Draws an animated arc spinner using the window's DrawList.
    — Uses ImGui::GetTime() for animation phase.
    — Renders the label text below the spinner.
    — Uses ImGuiWindow* internals (GetCurrentWindow()) which requires
      imgui_internal.h. This is the only place in the non-Render-tab code
      that uses imgui_internal besides AppShell.

  RenderBusyOverlay(message)
    — Fills the current window with a semi-transparent dark rect.
    — Drops an InvisibleButton over the whole window to block input.
    — Centers DrawSpinner in the window with the provided message.

These two functions are the entirety of the shared UI utility library.
There is no custom widget library beyond this. All other UI patterns are
inline in their respective module files.
