STACK APPLICATION — BUTTONS, MENUS, NAMING, AND FUNCTIONAL ORGANIZATION
=========================================================================
Researched from src/ source tree, May 2026

This document catalogs every button, menu, and interactive element in the
application with its exact label text, which file it is in, and notes on
naming quality and functional placement.

--------------------------------------------------------------------------------
SPLASH SCREEN
--------------------------------------------------------------------------------

The splash screen has no interactive elements. It shows:
  - The splash image (embedded from EmbeddedSplash.h)
  - A 4px progress bar at the bottom
  - Status text (e.g., "Loading project X of Y: <filename>", "Ready")

No buttons exist on the splash.

ROOT LEVEL: AppShell.cpp
--------------------------------------------------------------------------------

Modal: "Editor Project Already Open##AppShell"
  Trigger: Attempting to open a project in the Editor when one is already loaded.
  Message: "There is already a project open in the Editor tab. Would you like to
            save it before loading the new project?"

  Button: "Save & Continue"     (width 140px)
    — Saves the current project and then navigates to Editor with new project.
    — If the current project has no file name, opens the Save Name prompt.
  Button: "Discard & Continue"  (width 140px)
    — Discards the current editor project and loads the new one.
  Button: "Cancel"              (width 100px)
    — Closes the modal, no action.

Modal: "Save New Editor Project##AppShell"
  Trigger: The "Save & Continue" path when the current project has no file name.
  Message: "Enter a name for the current project:"

  InputText: ##ProjectName (unlabeled input, full-width)
  Button: "Save"     (width 100px)
    — If input is empty, saves as "Untitled Project".
  Button: "Cancel"   (width 100px)

NAMING NOTES (AppShell modals):
  "Save & Continue" and "Discard & Continue" are clear and appropriately paired.
  The ampersand is used consistently. "Cancel" is universally understood.
  The ## suffix on the popup ID ("##AppShell") is correct ImGui practice to
  avoid ID collisions. The popup titles contain the ## which means "AppShell"
  is part of the ID but not displayed — only the part before ## is shown.
  Wait — in ImGui, BeginPopupModal's first argument IS the title. Looking at
  the code: ImGui::BeginPopupModal("Editor Project Already Open##AppShell", ...)
  The ##AppShell is the ID disambiguation, the displayed title is
  "Editor Project Already Open". This is correct.

NAMING NOTES (Library):
  "Options" is vague — it opens a popup with import/export/refresh actions.
  "Import" would be more specific. "Options" is often used for settings, not
  primary workflow actions like import.
  
  "All Projects" and "Assets" as sidebar filter selects are clear.
  
  "Load Selected into Composite" is accurate but verbose. It appears three
  times in different contexts (project card menu, asset card menu, preview
  panel). Consistent wording across all locations is a positive.
  
  "Delete Selected (N)" showing the count is excellent UX — the user knows
  exactly how many items will be deleted.
  
  "Apply Tag" and "Remove Tag" beside each other with a shared text input
  is a simple tagging interface. The lack of any label on the input (only a
  placeholder) means there is no persistent visual affordance for what the
  input is for once text is entered.
  
  "Untagged only" as a checkbox label is slightly awkward compared to
  "Show untagged only" or "No tags".
  
  The "After" / "Before" labels on the compare view are drawn directly onto
  the image via DrawList with no background. They use hardcoded screen positions
  (10px from left, 55px from right, 10px from top). The text is small and
  white with 220 alpha — adequate but could be missed on light images.

NAMING NOTES (Editor):
  "SAVE TO LIBRARY" in all-caps is the primary call-to-action for the Editor.
  It is prominently placed at the top of the sidebar. Good.
  
  The sidebar tab order — Layers, Canvas, Selected, Pipeline — is not ideal
  for workflow. A user new to the Editor would first want to load an image
  (Canvas), then browse layers to add (Layers), then configure the selected layer
  (Selected), then reorder in the pipeline (Pipeline). The current order puts
  the "add layer" interface first and "load image" second, which is backwards
  for first use.
  
  "Available Modules" is the label for the layers list. This is unusual — "Effects"
  or "Layers" would be the industry standard term. The application calls these
  "layers" everywhere else ("Layers tab", "layer stack", "pipeline") but the
  header above the list says "Modules", creating a naming inconsistency.
  
  Layer categories are named well and color-coded, which aids scanning. "DAMAGE &
  GLITCH" is an unusual but accurate descriptor for compression artifacts, corruption,
  image breaks, and VHS effects. "OPTICS" is clear.
  
  The "x" delete button on each pipeline layer has no label. It is 20x20px and
  right-aligned. It is small and discoverable only by hovering near the right edge.
  There is no tooltip. This is a usability gap — deleting a layer is permanent
  (no undo system exists) and the button is tiny and unlabeled.
  
  The visibility checkbox in the pipeline has no label at all (##vis). A tooltip
  saying "Toggle layer visibility" would be appropriate. The eye icon is the
  industry convention here, but plain ImGui has no icon support by default.
  
  "Only Render Up To Active Layer" is long but accurate. The TextDisabled
  explanation below it is good — it prevents confusion about what this option does.
  
  "[ ZOOM LOCKED ] - Press 'L' to unlock" is clear and specific. The keyboard
  shortcut 'L' is not documented anywhere else — only in this runtime tooltip.
  "Scroll to Zoom | 'L' to Lock | Movement Pans" is the unlocked state hint.
  The 'L' shortcut is not shown in any menu or tooltip before the user discovers
  it by hovering on the viewport.
  
  The comparison hover behavior (hovering the image fades in the original for
  comparison) has no affordance whatsoever. There is no tooltip, no label, nothing
  to tell the user this feature exists. The TextDisabled status line says nothing
  about this.

NAMING NOTES (Bundler):
  "Bundler Inputs" and "Output Directory" are clear.
  
  "Build Mode" option labels: "Single HTML", "Per-file Minify", "Bundle by Type"
  — These are accurate and distinct. They correctly describe what each mode does
  at a high level. A first-time user might want a tooltip on each, but the labels
  are not misleading.
  
  "Detect Tools on PATH" is specific and honest — it tells the user exactly where
  tools are looked for. The button disappearing after detection and being replaced
  by status text with "Re-detect" is clean UX.
  
  "Scan Inputs" and "Build" are a two-step workflow. The disabled state of "Build"
  until scan has run is correctly enforced. However, the height of both buttons
  is 28px while all other buttons in the settings panel use height 0 (default).
  This creates visual inconsistency — the primary action buttons are taller, which
  is actually good for discoverability, but the inconsistency could be intentional
  or accidental.
  
  The "Project Files" panel title doesn't describe what you're seeing well for a
  bundler — "Dependency Graph" or "File Graph" would be more accurate, since the
  panel shows a scanned dependency tree, not just a list of project files.
  
  "Bundler Diagnostics" is accurate. "Clear Logs" is clear.
  
  Auto-scroll to bottom in the log panel is the correct behavior for an output log.

RENDER TAB: RenderTab.cpp (representative — file is 4046 lines)
--------------------------------------------------------------------------------

The Render tab contains the most UI in the application. Only major groupings
are cataloged here.

TOOLBAR:
  — Project name display, save button, unsaved-changes indicator.
  — View mode selector (Unlit / Path Trace).
  — Camera options toggle, Final Render Settings toggle, Test Scenes toggle.
  — Reset Scene button.
  — Transform mode buttons (Translate W / Rotate E / Scale R) with keyboard hints.
  — Transform space toggle (Local / World).

SCENE PANEL:
  — Object list (primitives, lights).
  — Add buttons for: Sphere, Cube, Plane, Imported Mesh, Point Light, Spot Light,
    Area Light, Directional Light, Laser Light.
  — Import mesh button opening the import dialog.
  — Select/deselect buttons.
  — Delete selected button.

INSPECTOR PANEL:
  — Context-sensitive depending on selection (primitive, light, material, camera,
    environment, render settings, postprocessing).
  — For primitives: Transform (position, rotation, scale), Material assignment.
  — For lights: Type, color, intensity, position, direction.
  — For material: Base type (Diffuse/Metal/Glass), roughness, IOR, transmission,
    color, clearcoat.
  — For environment: HDR intensity, fog color.
  — For camera (in Camera window): FOV, position, yaw, pitch, white balance,
    exposure.
  — For denoiser: Mode (Off/Bilateral/A-Trous), strength, debug view selector.
  — For viewport: Performance mode (Auto/Exact/Proxy).
  — For final render: Resolution, sample count, denoiser export mode.

NAMING NOTES (Render — selective):
  All enum label functions (ViewModeLabel, DenoiserModeLabel, etc.) live in the
  anonymous namespace and are used purely to feed Combo/RadioButton displays.
  This is a clean separation: the display strings are not scattered in the enum
  definitions.
  
  "A-Trous" is a technical denoiser name — acceptable for a render tool where
  the audience knows the term.
  
  "Smart" termination mode is vague next to "Brute Force" and "Optimized" — the
  others have connotations but "Smart" could mean anything.
  
  "Keep Original Scale" and "Auto Fit Scene" for import scale modes are clear.
  
  "W/E/R" keyboard shortcut hints appear in the toolbar next to transform mode
  buttons — this is good discoverability for non-obvious shortcuts.

NAMING NOTES (Composite):
  The aspect ratio presets use internal enum names like Ratio1x1, Ratio16x9
  which will map to display labels (not verified in detail, but common convention).
  
  "Save to Library" and "Export PNG" are clear and distinct — saving to the
  internal library vs. exporting to a user-chosen file path.
  
  CompositeSnapModePreset enum has: Full, ObjectOnly, Off, Custom — these are
  self-explanatory snap behavior modes.
