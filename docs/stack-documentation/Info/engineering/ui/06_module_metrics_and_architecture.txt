SINGLETONS IN USE
--------------------------------------------------------------------------------

LibraryManager::Get()
  — Used by: LibraryModule, EditorModule, EditorSidebar, RenderTab, AppShell
  — The most widely accessed singleton. Every module that reads from or writes
    to the library touches this singleton.
  — Carries: project list, asset list, async task states, save/import/export
    status text.

Async::TaskSystem::Get()
  — Used by: AppShell (pump), EditorModule, RenderTab, LibraryManager
  — Carries the thread pool and the main-thread task queue.

TagManager::Get()
  — Used by: LibraryModule only
  — Carries: tag-to-file mappings persisted to disk.

LAYER SYSTEM ARCHITECTURE
--------------------------------------------------------------------------------

LayerBase (abstract base, LayerBase.h) defines the interface:
  InitializeGL()    — compile shaders
  Execute(inputTex, width, height, quad)  — run GPU effect
  ExecuteWithSource(inputTex, sourceTex, width, height, quad)  — optional override
  RenderUI()        — draw ImGui controls (pure virtual)
  RenderUI(editor*) — optional override if the layer needs editor context
  Serialize()       — return JSON
  Deserialize(json) — restore from JSON
  GetDefaultName()  — layer type name (pure virtual)
  GetCategory()     — category string (pure virtual)
  GetName()         — instance name if set, else default name

28 concrete layer types are registered in two places:
  1. EditorModule::AddLayer() — switch(type) to instantiate (lines 93-123)
  2. EditorModule::DeserializePipeline() — if-else chain on type string (lines 250-278)

The duplication between these two is a maintenance concern. If a new layer is
added, both blocks must be updated. There is no self-registration mechanism.
The LayerType enum (EditorModule.h lines 17-47) is the authoritative list.

TYPE STRING MISMATCH RISK:
  The DeserializePipeline chain uses string literals that must match the
  Serialize() output of each layer (e.g., j["type"] = "Adjustments").
  Several aliases are handled: "Dither" || "Dithering", "CellShading" || "Cell",
  "Palette" || "PaletteReconstructor", "Edge" || "EdgeEffects",
  "AiryBloom" || "AiryDiskBloom". These aliases indicate that the type strings
  have changed at some point and backward compatibility was patched in manually.
  
  A type string registry (static constexpr const char* kLayerTypeAdjustments
  used in both Serialize and DeserializePipeline) would eliminate the risk of
  these diverging.

LAYER DISPLAY NAME DUPLICATION:
  LibraryModule.cpp (anonymous namespace, lines 61-81) contains LayerDisplayName()
  which maps type strings to user-visible names (e.g., "ColorGrade" -> "3-Way
  Color Grade"). These display names are used when previewing the layer stack
  in the Library's project preview popup. This is a separate mapping from the
  labels used in LayersTab.cpp. The two should match but are maintained
  independently.

  LayersTab.cpp buttons use:
    "3-Way Color Grade"          for LayerType::ColorGrade
    "Heatwave & Ripples"         for LayerType::Heatwave
  LibraryModule LayerDisplayName uses:
    "3-Way Color Grade"          for "ColorGrade" — matches
    "Heatwave & Ripples"         for "Heatwave"   — matches
  But the mapping is duplicated. Any change to one name requires two file edits.

ASYNC TASK STATE: HOW IT INTEGRATES WITH UI
--------------------------------------------------------------------------------

Async::TaskState has values: Idle, Queued, Running, Applying, Failed.
Async::IsBusy() returns true for Queued, Running, Applying.

The UI queries state each frame. The state machine transitions:
  Idle -> Queued (when task is submitted)
  Queued -> Running (when worker thread picks it up — not observable from UI)
  Running -> Applying (when worker posts to main thread, before main-thread work)
  Applying -> Idle (after main-thread work completes)
  Any -> Failed (on error)

The "Applying" state is used to keep the busy overlay visible while the main
thread processes results (e.g., uploading decoded pixels to OpenGL). This
prevents a frame where the spinner disappears before the data is actually applied.

The pattern is implemented identically in:
  EditorModule — source load and export tasks
  LibraryManager — save, import, export, load, project load tasks

The generation counter pattern (m_SourceLoadGeneration, m_ExportGeneration) is
used to discard stale async results if a new task is submitted before the old one
finishes. This is a correct and safe implementation.

PERSISTENCE ARCHITECTURE
--------------------------------------------------------------------------------

StackBinaryFormat (Persistence/StackBinaryFormat.cpp):
  All projects are saved as binary blobs with JSON payloads. The format handles
  editor projects, composite projects, and render projects via projectKind field.
  
  Constants:
    kEditorProjectKind    — "editor"
    kCompositeProjectKind — "composite"
    kRenderProjectKind    — "render"

  These constants are checked in LibraryModule to determine which context menu
  items to show (Open in Editor vs. Open in Composite vs. Open in Render).

Project file names are used as unique identifiers throughout. LibraryManager
stores the library on disk and loads from it. File names are used as keys in:
  - TagManager (tag storage)
  - LibraryModule selection sets (m_SelectedProjects is a set of file names)
  - LibraryModule preview state (m_RenameTargetFileName)
  - AppShell (m_ActiveSyncLayerId tracks a composite layer ID, not a file name)

The Composite module saves its layout via imgui.ini substring (m_WorkspaceLayoutIni).
This is the only persistence that depends on ImGui internals — it saves and
restores the dock node state. This would break under a framework switch.

src/ThirdParty/ is referenced by several modules but not listed in the

These are header-only or single-header libraries embedded in the project.

WHAT WOULD BREAK IF RENAMED / MOVED
--------------------------------------------------------------------------------

If "Inspector Panel Sidebar" were renamed:
  EditorSidebar.cpp::Render() line 18 + EditorModule.cpp line 213 must match.

If "Canvas Viewport" were renamed:
  EditorViewport.cpp::Render() line 33 + EditorModule.cpp line 214 must match.

If "Scopes Panel" were renamed:
  EditorScopes.cpp::Render() line 83 + EditorModule.cpp line 215 must match.

If "Bundler Settings", "Project Files", "Bundler Diagnostics" were renamed:
  BundlerModule.cpp::RenderUI() lines 132-134 (DockBuilderDockWindow) + lines
  138, 143, 148 (Begin calls) must all match.

If the root tab bar enum values changed order:
  AppShell.h m_RequestedTab default would need update.
  All callers passing integer indices (0=Library, 1=Editor, 2=Composite,
  3=Render, 4=Bundler) would need update. These include LibraryModule context
  menu items (if (m_CachedActiveTab) *m_CachedActiveTab = 0/2) and the
  RootTabId enum values.

The RootTabId enum and the tab label strings are declared in an anonymous
namespace local to AppShell.cpp. They are not visible to other modules.
Modules that need to trigger a tab switch pass the integer value (0-4) via
the int* activeTab parameter. If the tab order changes, every site that uses
a hardcoded integer must be updated. There are no named constants shared
between AppShell and the modules for tab indices.
