STACK APPLICATION — UX COMMON SENSE AND EASE-OF-USE AUDIT
===========================================================
Researched from src/ source tree, May 2026

This document evaluates the application's UI from a practical usability
standpoint — whether workflows make sense, whether discoverability is adequate,
and where real friction exists for a user trying to accomplish tasks.

--------------------------------------------------------------------------------
FIRST-RUN EXPERIENCE
--------------------------------------------------------------------------------

On first launch, the app shows a splash screen for at least 2 seconds while
scanning the library. After the splash, the application opens on the Library
tab (tab index 0 = the default, set via m_RequestedTab = 0 in AppShell.h).

The Library tab shows either:
  a) A grid of project thumbnails if any projects exist.
  b) "No projects found in the library." if empty.

There is no tutorial, onboarding tooltip, or first-use hint. A user who has
never seen the app sees a header area with an "Options" button and a search bar,
a left sidebar labeled "FILTERS", and an empty or filled grid.

The "Options" button is the only button in the Library tab's top area. For a new
user who wants to create a project or load an image, the workflow is:
  Library → (no create button) → Editor tab → Canvas → "Load Image..."

This path is not guided. A new user might spend time looking for a "New Project"
button in the Library tab that does not exist. The Library tab is a gallery, not
a creation tool, but it is the default landing screen.

The first-use friction is significant. There is no global action in the Library
that says "start editing" or "open an image in the Editor". The user must discover
on their own that the Editor tab is where work begins.

FILE DROP SUPPORT:
  Files can be dragged onto the application window. HandleDrop() in AppShell.cpp
  routes dropped files through LibraryManager::RequestImportAndLoad(), which
  auto-navigates to the appropriate tab. This is a good shortcut, but it is
  completely undocumented in the UI.

--------------------------------------------------------------------------------
LIBRARY TAB — WORKFLOW ASSESSMENT
--------------------------------------------------------------------------------

WHAT WORKS WELL:
  - Thumbnail grid with automatic flow-wrap based on window width is standard
    and clear.
  - Double-click to open preview is a universal convention.
  - Ctrl+click for multi-select follows Windows Explorer convention.
  - The compare slider in the preview popup (before/after) is immediately
    interactive without any setup.
  - Tag filtering with checkboxes in the sidebar is visible and persistent.
  - "Delete Selected (N)" showing the count is excellent — prevents accidental
    mass delete confusion.
  - The filter panel is resizable by dragging the splitter, which is a good
    touch (though not visually obvious without hovering first).

WHAT IS CONFUSING:
  - "Options" button opens import/export/refresh actions, not settings. The
    word "Options" implies configuration, not workflow actions.
  - The tag input field ("New tag...") and "Apply Tag" / "Remove Tag" buttons
    require items to be selected first. There is no visual feedback if nothing
    is selected and you click "Apply Tag" — it silently does nothing.
  - "Library refresh is automatic." at the bottom of the sidebar is informational
    but implies users might wonder if they need to manually refresh. A better
    approach would be a subtle "last refreshed" timestamp.
  - The status text (import status, export status, save status) is rendered as
    TextDisabled between the header and the splitter. It is small and gray,
    easily missed during a busy operation.
  - "All Projects" and "Assets" are Selectable items that look similar to the
    tag checkboxes. Users might not immediately recognize that these are mode
    switches, not filters. They have no visual distinction (checkbox vs. text-row).

PREVIEW POPUP:
  - The preview takes over the full screen, which is appropriate for examining
    images. The compare slider is functional.
  - However, the close mechanism is not documented. There appears to be a
    close button somewhere in the popup (based on the boolean
    `closeProjectPreview` flag in RenderPreviewPopup), but its exact label
    is not fully confirmed in the code read. If Escape closes it, that is
    not labeled.

--------------------------------------------------------------------------------
EDITOR TAB — WORKFLOW ASSESSMENT
--------------------------------------------------------------------------------

WHAT WORKS WELL:
  - Three-panel layout (sidebar, viewport, scopes) follows standard image editor
    conventions (Photoshop/Lightroom-style).
  - "SAVE TO LIBRARY" button at the top of the sidebar is prominently placed.
    Its disabled state during a save operation relabels it to "SAVING TO LIBRARY..."
    which is clear state feedback.
  - Layer visibility checkbox in the pipeline is in the correct position
    (left of the layer name, standard for layer panels).
  - Drag-and-drop reordering in the Pipeline tab is functional and correctly
    updates the selection index.
  - The scopes panel (Histogram/Vectorscope/RGB Parade) auto-updates on a
    throttled timer. Users don't need to trigger it manually.
  - The comparison hover in the viewport (processing output vs. original) is a
    nice feature for evaluating changes.

WHAT IS CONFUSING:
  - Tab order: "Layers, Canvas, Selected, Pipeline" — the workflow order should
    be "Canvas, Layers, Pipeline, Selected". Users need to load an image before
    they can do anything, but Canvas is the second tab. They see the layer
    browser first (which is useless until an image is loaded).
  - "Available Modules" header above the layer button list — the application
    calls them "layers" everywhere else. This inconsistency creates confusion.
    The canonical term should be chosen and used uniformly.
  - The "Selected" tab auto-focuses when a layer is added (via
    m_FocusSelectedTabNextRender). This is good — it takes the user directly to
    the controls for the layer they just added. However, if the user switches
    away and back, the auto-focus doesn't re-trigger.
  - "Hankel (Optical) Blur" is an obscure technical name. Most users won't know
    what a Hankel transform blur is. The parenthetical "(Optical)" helps slightly
    but it's still opaque.
  - The viewport status hint ("Scroll to Zoom | 'L' to Lock | Movement Pans")
    is always visible overlaid on the image in the top-left. This text takes
    up viewport real estate. It could be replaced with a bottom status bar or
    a tooltip that appears on first hover.
  - The "x" delete button on pipeline layers:
    - No tooltip explaining it deletes the layer.
    - No undo — deletion is permanent.
    - 20x20px is the minimum comfortable click target, but for a destructive
      action this is small.
    - "x" is universally understood as close/delete but should at minimum have
      a tooltip "Remove layer (permanent)".
  - The color picker mode (triggered by certain layers) changes the viewport
    cursor to a Hand and shows a pixel magnifier. There is no way for the user
    to cancel out of color pick mode except by clicking a pixel (which triggers
    the pick). If the user accidentally enters color pick mode, Escape or right-
    click cancelling is not documented.
  - The "Only Render Up To Active Layer" checkbox in Canvas tab — the word "Active"
    means the selected layer in the Pipeline tab, not the currently visible/enabled
    one. The TextDisabled explanation clarifies this, but "Selected" would be
    a more accurate word than "Active".

--------------------------------------------------------------------------------
BUNDLER TAB — WORKFLOW ASSESSMENT
--------------------------------------------------------------------------------

WHAT WORKS WELL:
  - The two-step workflow (Scan → Build) is enforced by the UI. Build is
    disabled until a scan has completed. This prevents users from trying to
    build without first scanning.
  - The progress bar appears only during building and disappears after completion.
  - The log panel auto-scrolls to the bottom, which is appropriate for a build
    output console.
  - Color-coded log entries (red = error, orange = warning, gray = info) follow
    standard conventions.
  - The reference count summary (found/resolved/unresolved) after scanning gives
    immediate feedback on graph health.
  - Build result summary (processed, minified, copied, failed, input size, output
    size, savings %) is comprehensive and helpful.

WHAT IS CONFUSING:
  - "Project Files" panel name is misleading — the panel shows a dependency graph,
    not a list of project files in the normal sense.
  - The "Detect Tools on PATH" button disappears after detection and is replaced by
    tool status rows + a SmallButton "Re-detect". The SmallButton is small and
    positioned after the tool status rows without a visual separator. It could be
    missed.
  - The filter Combo box in Project Files says "Filter" as the label, which is
    redundant with its function. "Show Type" or "File Type" would be more specific.
  - "Show References" checkbox next to the Filter combo — this changes the tree
    from flat rows to expandable nodes. The behavior change is significant but
    the control is small and unlabeled beyond the checkbox text.
  - The input list (Bundler Inputs) is a 100px-tall scrollable child with no
    separator or visual header beyond "Bundler Inputs" text above it. Individual
    paths are shown as TextWrapped, which means long paths wrap and can make the
    list hard to read. There is no per-item remove button — only "Clear Inputs"
    removes everything.
  - There is no way to remove a single input path. If you add 5 files and one
    was a mistake, you must "Clear Inputs" and re-add all four correct ones.

--------------------------------------------------------------------------------
RENDER TAB — WORKFLOW ASSESSMENT (HIGH LEVEL)
--------------------------------------------------------------------------------

WHAT WORKS WELL:
  - The three-panel layout (Inspector left, Scene right, Viewport center) mirrors
    3D application conventions (Maya, Blender left-panel inspector, right-panel
    outliner, center viewport).
  - Keyboard shortcuts W/E/R for transform modes with visible labels in the toolbar.
  - The camera window and final render settings window are floatable/dockable
    sub-windows rather than crammed into the inspector. This keeps the inspector
    focused on scene objects.
  - Test Scenes (validation scenes like Cornell Box) as a separate toggleable
    window is a good way to separate debugging from production workflow.
  - The label functions (ViewModeLabel, DenoiserModeLabel, etc.) in the anonymous
    namespace mean that enum values have one canonical string representation used
    everywhere — Combos, status displays, and debug text all show the same name.

WHAT IS CONFUSING:
  - "Smart" termination mode for the path tracer has a vague name compared to
    "Brute Force" and "Optimized". Users can't tell from the name what "Smart"
    actually does differently.
  - "A-Trous" denoiser mode is a technical name not familiar to general users.
    A parenthetical like "A-Trous (Wavelet)" would help.
  - The RenderTab is the most technically complex tab with the most UI controls.
    Without tooltips on every control, users with no rendering background can
    easily misconfigure settings (e.g., excessive ray bounces for non-glass scenes,
    or leaving proxy mode active for a final render).
  - "Proxy" viewport performance mode — the name is accurate (uses a lower-
    resolution proxy viewport for speed) but users might mistake "Proxy" for
    something related to network proxies.

--------------------------------------------------------------------------------
COMPOSITE TAB — WORKFLOW ASSESSMENT (HIGH LEVEL)
--------------------------------------------------------------------------------

WHAT WORKS WELL:
  - Layer pane with visibility and lock toggles follows standard compositing app
    conventions.
  - Blend modes list (Normal, Multiply, Screen, Add, Overlay, SoftLight,
    HardLight, Hue, Color) matches Photoshop/GIMP conventions exactly.
  - Aspect ratio presets in the Export panel (1x1, 16x9, 9x16, etc.) are
    immediately recognizable without needing numeric entry.
  - The snap system with multiple snap types (objects, centers, canvas center,
    export bounds, spacing, rotation, scale) is comprehensive. The preset mode
    (Full/ObjectOnly/Off/Custom) gives quick access without exposing all toggles.
  - Save to Library vs. Export PNG distinction is clear.

WHAT IS CONFUSING:
  - The workspace layout is saved per-session via m_WorkspaceLayoutIni but the
    persistence mechanism is bespoke (storing imgui.ini as a string). If the
    application crashes mid-session, the layout may not save.
  - The "Open in Editor" flow from Composite (selecting a project layer, switching
    to Editor, editing, switching back) is automatic via OnTabChanged() in AppShell.
    This works but the sync is silent — the user is not notified that the Composite
    layer has been updated. A brief status indicator after returning to Composite
    would confirm the sync happened.
  - Export bounds mode "Auto" uses the bounding box of visible layers, which may
    not match the user's intended output. The boundary is shown as a draggable
    overlay, which is good, but the mode label "Auto" does not describe what
    "auto" means (it auto-fits to layer content).

--------------------------------------------------------------------------------
CROSS-CUTTING ISSUES
--------------------------------------------------------------------------------

UNDO SYSTEM:
  There is no undo system in any tab. In the Editor, deleting a pipeline layer
  is permanent. In the Composite, removing a layer is permanent. In the Bundler,
  clearing inputs is permanent. Only the Library's delete action has a confirmation
  popup ("Delete Selected (N)"). The Layer pipeline delete ("x" button) has none.

  This is the most significant usability gap in the application.

KEYBOARD SHORTCUTS:
  The only documented keyboard shortcuts are in the Render tab toolbar (W/E/R for
  transform modes). In the Editor viewport, 'L' toggles zoom lock. No other
  keyboard shortcuts are visible in any menu, tooltip, or help text.
  
  The application supports ImGuiConfigFlags_NavEnableKeyboard, which enables
  keyboard navigation of the ImGui UI (Tab to advance focus, Space/Enter to
  activate). This is good for accessibility but not specifically documented.

TOOLTIPS:
  There are NO ImGui::SetTooltip() or ImGui::BeginTooltip() calls found in any
  of the main module files during this research. The absence of tooltips is a
  significant discoverability gap, especially for:
    - The "x" delete button on pipeline layers.
    - The visibility checkbox (##vis) on pipeline layers.
    - The comparison hover in the Editor viewport.
    - The file-drop behavior.
    - Layer effect names in the Layers tab that are not self-explaining.

STATUS TEXT CONSISTENCY:
  Status messages use three different display methods:
  1. TextDisabled — used for most status/feedback text. Gray and easy to miss.
  2. TextColored — used for error states (red), success (green), and info.
  3. ImGuiExtras::RenderBusyOverlay — used for blocking async operations.
  
  The line between when a status message uses TextDisabled vs. a more prominent
  display is inconsistent. For example, after a successful export, the status
  "Rendered image exported." appears as TextDisabled — a success message in gray
  is very low visibility.

NAMING INCONSISTENCIES SUMMARY:
  - "Layers" (tab label, pipeline content) vs. "Modules" (Layers tab header)
  - "Active" layer vs. "Selected" layer (Canvas tab option vs. actual behavior)
  - "Options" button (Library) which contains import/export actions, not settings
  - "Project Files" panel (Bundler) which shows a dependency graph
  - The project preview popup title is "Library Project Preview" but the window
    is full-screen with no visible title bar — the title is never shown to users
