Core Diagnosis
The freezes are real and explainable: RAW Workspace is partly async, but the expensive follow-up work often returns to the UI thread before the user sees a loading state.
The biggest offenders are:
RAW source selection loads/saves synchronously
[EditorModuleRawWorkspace.cpp (line 938)](/D:/Program Development/Stack/src/Editor/Internal/EditorModuleRawWorkspace.cpp:938) can save the old RAW project, stage/load the new project, persist catalog/app state, and only then return.
Existing project selection calls [LoadRawWorkspaceProjectForSource (line 263)](/D:/Program Development/Stack/src/Editor/Internal/EditorModuleProjectLifecycle.cpp:263), which does ReadProjectFile, PNG decode, ApplyLoadedProject, graph validation, and dirty-state work inline.

Scan completion does a second heavy pass on the UI thread
The folder walk is backgrounded, but when it finishes, [RequestRawWorkspaceScan (line 699)](/D:/Program Development/Stack/src/Editor/Internal/EditorModuleRawWorkspace.cpp:699) posts back to main and runs thumbnail classification, [DiscoverProjects (line 315)](/D:/Program Development/Stack/src/Raw/RawWorkspaceProjects.cpp:315), catalog writes, app-state writes, and thumbnail generation kickoff.

Catalog persistence is far too eager
[PersistRawWorkspaceCatalog (line 993)](/D:/Program Development/Stack/src/Editor/Internal/EditorModuleRawWorkspace.cpp:993) rewrites the whole catalog after selection, scan completion, each thumbnail result, and final thumbnail completion. On a 178-file folder, that can become death by a thousand paper cuts.

Thumbnail texture creation happens inside draw code
[GetRawWorkspaceThumbnailTexture (line 529)](/D:/Program Development/Stack/src/Editor/Internal/EditorModuleRawWorkspace.cpp:529) does filesystem checks, stbi_load, and GL texture upload during UI rendering. Scrolling or showing a tile for the first time can hitch.

“Fast preview” is not truly cheap yet
The preview cap shrinks the final output, but RAW upload/prep still often uses full-size data in [RawGpuPipeline.cpp (line 1466)](/D:/Program Development/Stack/src/Raw/RawGpuPipeline.cpp:1466). Snapshot building can also copy full source buffers before the render worker starts.

RAW loading is under-communicated
The editor has busy overlays, but RAW Workspace mostly shows inline text/progress. Worse, several expensive operations happen before any overlay can appear.

What Should Preload Before Showing
Keep this small and deterministic:
RAW app-state JSON.
LibRaw runtime availability check.
Settings/appearance/icons already expected at startup.
I would not block first paint on scanning the last RAW folder or loading full selected RAW projects. That would just move the freeze earlier. Instead, the app should show once small prerequisites are ready, then RAW Workspace should enter a clear “restoring workspace…” state.
Recommended Implementation Order
Loading state and overlays
Add explicit RAW Workspace states: scanning, applying scan, discovering projects, loading selected source, saving previous source, generating thumbnails, rendering preview/full. Dim/block the RAW content while destructive or selection-changing work is active.

Batch/debounce catalog and app-state writes
Stop writing catalog/app state on every click and every thumbnail. Mark dirty, batch results, flush on timer/lifecycle/explicit save.

Move scan apply/discovery off the UI thread
Keep main-thread scan completion to a tiny immutable state swap. Do ClassifyThumbnails, DiscoverProjects, and catalog skeleton preparation in worker stages.

Make RAW source selection async
Selection should set selected key immediately, show loading, then worker-read/decode project data. Feed existing projects through BeginDeferredLoadedProjectApply() instead of direct ApplyLoadedProject().

Thumbnail pipeline
Background-decode thumbnail PNGs to CPU buffers, then upload textures through a small per-frame GL upload budget. No stbi_load in tile rendering.

True RAW proxy preview
Make capped previews actually use downsampled/proxy RAW input or staged lower-resolution uploads, then settle to full-res after quiet.

That order attacks the freezing you described in the same order the user feels it: opening RAW tab, loading folder, clicking images, then adjusting/rendering.
